generic policy that changes rarely; everything that goes stale as curation proceeds lives here:
the pinned upstream revisions, the reviewed scope exceptions, the generated counts, per-game
promotion notes, and who is working on what.

Keep it synchronized after every material change. Generated reports remain the numerical source of
truth; if regeneration disagrees with a count below, investigate the diff and update this file
rather than preserving a stale literal.

Williams Tales of the Arabian Nights (`williams.tales-of-the-arabian-nights.1996`) was curated on 2026-08-07 as the fourth WPC-95 machine, reusing `controllers/pinmame/wpc-95.json` unchanged (confirmed from the pinned driver's own `GEN_WPC95` field, not from the task brief). It covers the five-driver `totan_*` clone tree (`totan_14` parent, `totan_04`/`totan_12`/`totan_13` earlier firmware, and `totan_15c`, a 2016 community "Competition MOD" ruleset that runs on the identical physical hardware and addresses). Its switch-matrix opto sweep found **zero disagreement** with pinned PinMAME: the manual's seven-address opto column (matrix column 3, rows 1-7, addresses 31-37 -- the trough optos plus the left/right inlane "cage" optos) matches `totanGameData`'s inverted-switch mask (`{0x00,0x00,0x00,0x7f,0x00,0x00,0x00,0x00,0x00,0x00,0x00,0x00}`) exactly, the same clean result Bally The Addams Family produced. `coverage.missing` is `["spatial_placement", "unresolved_conflicts"]`; it carries one unresolved conflict (`conflict.gi-string-3-playfield-binding`) and two unresolved spatial gaps (GI addresses 3 and 4).

Two things from it generalise.

1. **A retained table's own script can visually contradict its own manual's wiring table, and the manual wins for a device's spatial classification.** The manual documents GI address 2 (printed Illumination String 3) as backbox-insert-panel-only (`#44` bulb, `J106` connectors, no Playfield column entry), while the two genuinely playfield-wired strings are addresses 3 and 4 (`#555` bulbs, `J105` connectors). The retained (non-VPW, 944-file, no VPW authorship) known-working script's `Sub UpdateGI` implements *only* `Case 2`, wiring it to a large playfield-wide dimming effect across dozens of textures, while addresses 0, 1, 3, and 4 have no case and produce zero visual effect. Rather than trusting the script's runtime behavior over the manual's physical wiring for a backbox device, this curation kept GI address 2 a `not_applicable`/`cabinet_or_service` record per the manual, recorded the disagreement as a first-class unresolved conflict, and left the manual's two genuine playfield strings (3, 4) with no fabricated placement since no VPX object binds to either. This is the first WPC-95 game in the project where the evidence-authority split between "runtime semantics" (script) and "physical construction" (manual) produced a genuine, principled disagreement about where a conflict should be recorded rather than which value is correct.
2. **Printed solenoid circuits normally reserved for upper flippers can drive plain, untranslated non-flipper devices with no address remapping at all**, a variant of the pattern Indiana Jones and Star Trek: TNG already established for *switch* columns. Printed circuits 33-36 ("Upr. Rt./Lt. Power/Hold") drive a playfield diverter gate and two independent devices (Vanish Magnet, Loop Post Diverter); because `totanGameData.hw.flippers` declares `FLIP_SOL(FLIP_L)` only (no `FLIP_UR`/`FLIP_UL` bit), pinned PinMAME's `core_getSol` never routes these four addresses through any flipper-coil path, so they pass straight through as public 33-36 with **no** translation -- unlike the lower-flipper pair, where printed 29-32 do translate to public 45-48 via `CORE_FIRSTLFLIPSOL`. Check `hw.flippers`' exact bit composition before assuming any upper-circuit address needs remapping.

The physical family is the five-driver `totan` clone tree (`totan_14` parent plus `totan_04`/`totan_12`/`totan_13` firmware revisions and the `totan_15c` community ruleset mod); every driver is physically identical.

Williams Medieval Madness (`williams.medieval-madness.1997`) was promoted on 2026-08-05 and is the first author-ready Williams WPC machine. It introduced the `pinmame.wpc-95` controller profile, which every later WPC-95 game should reuse instead of `pinmame.wpc-alpha`.

Bally Attack From Mars (`bally.attack-from-mars.1995`) was promoted on 2026-08-05 as the second WPC-95 machine, incorporating and superseding external PR #2. It is the first definition to enumerate PinMAME's two auxiliary lamp columns: `afmGameData` declares `lampCol = 2`, and the sixteen saucer-L.E.D. addresses 91-98 and 101-108 are shifted in serially by public solenoids 37 and 38. Reuse that pattern for any other game whose `core_tGameData` declares extra lamp columns, and note that WPC-95 auxiliary outputs 37-40 are mirrored at 41-44 while `custSol` duplicates appear from 51 upward. Its curation also recorded a genuine pinned-PinMAME defect worth remembering: `afm.c` names the two loop gates the opposite way round from the manual and from both retained known-working scripts, and is internally inconsistent because its `/* 33 */` and `/* 34 */` comments contradict its own `WPC_FLIPPERCOIL95` bit reads. Verify emulator-side left/right naming against the printed table before trusting it.

Williams Monster Bash (`williams.monster-bash.1998`) was promoted on 2026-08-06 as the third WPC-95 machine and the first selected by Pinside Top 100 rank (it is rank 10 on the 2026-08-02 solid-state list), and **demoted back to `partial` the same day**: an independent review found that public switches 74-78 (Dracula Position 5-1) are printed normally-closed opto interrupters on the A-21402 Defender Switch Board Assembly, shaded "OPTO, TYPICALLY CLOSED" on the printed switch matrix like 31-36 and 42/43, but pinned PinMAME's `mbGameData` inverted-switch mask leaves column 7 at `0x00` and does not normalize them, while PinMAME's own `mb_mech[2]` table asserts them at their step ranges in what reads as the opposite sense. That asymmetry is now a first-class, unresolved `conflicts` entry (`conflict.dracula-position-opto-not-normalized`); `coverage.dimensions.physical_wiring = "conflicted"` and `coverage.missing = ["polarity", "unresolved_conflicts"]`. Resolving it needs a LibPinMAME gameplay-harness trace of a legal `mb_10`/`mb_106b` ROM observing the idle public state of 74-78 and their transitions as the Dracula motor steps through its 90-step range. It reuses `pinmame.wpc-95` unchanged and declares neither `custSol` nor `lampCol`, so it is otherwise the clean baseline for a WPC-95 game without auxiliary columns. Six things from it generalise.

1. **A same-titled arcade video game can masquerade as the manual.** Internet Archive items `monster_bash_schematics_ptm` and `monster_bash_ptm` are the 1982 Sega/Gremlin arcade video game, not the pinball machine: their sheets read `CPU BOARD 800-3278`, `2716 EPROM BOARD 800-3277`, `Video Board 800-3290`, `Sound Board 634-0316`. Render a page and check manufacturer and board part numbers before citing any manual. Late Williams manuals carry their own Section 3 wiring and schematics, so a separate schematics item is usually unnecessary.
2. **A WPC game can ship with no knocker.** Printed solenoid addresses 04 and 07 have populated power-driver transistors (Q67, Q69) but no voltage and no drive connection in the playfield, insert or cabinet columns, and no solenoid row anywhere uses the cabinet columns. PinMAME's `mb.c` still defines `#define sKnocker 7` and the retained script plays a knocker sound, because the WPC-95 OS pulses driver 7 as its standard knocker output. Record the address as enumerated-but-unfitted and cite all three sources; do not create the device. The blank-connection pattern, not the presence of a transistor, is what proves nothing is fitted.
3. **Fliptronic positions get repurposed for non-flipper devices.** F7, positionally the upper-left flipper EOS at public 117, is the Center Spinner. That is why `mbGameData` sets `FLIP_SW(FLIP_L|FLIP_U)` on a game with no upper flippers. Check the printed Fliptronic block on every WPC-95 game before assuming 111-118 are all flipper hardware.
4. **The printed flipper numbering is not the public address.** Manuals number the flipper circuits 29-36 as power/hold pairs, so printed 29/30 (lower right) is public 45/46 and printed 31/32 (lower left) is public 47/48, while printed 33-36 happen to equal public 33-36. Keep the printed numbers only as `manual.address` aliases.
5. **Scoped asterisks and the Cabinet columns both matter.** The footnote "these general illumination strings do not brighten and dim, they are always on" carries the asterisk on GI 04 and 05 only, so the three playfield strings do dim. GI 05 is also the one row on the page with a cabinet connection (J104-3 / J104-1), so the five printed strings split playfield / backbox insert panel / backbox-plus-cabinet and must not all be treated as playfield.
6. **Expect internal typos and resolve them by the symmetric partner.** The lamp matrix reads DRAC-ATTTACK, QUARTER MOOM, THREE-QUARTERS MOON and LEFT GARGOYLE where the parts list reads DRAC-ATTACK, QUARTER MOON, THREE-QUARTER MOON and LEFT GARGLE. Lamp 48 was settled by its partner insert 25, which reads RIGHT GARGLE on both pages; the Bride insert trio is PRIMP / WARM UP / GARGLE. Prefer the parts list for labels.

Its twelve documented projections are the same class Medieval Madness already established and are enumerated in `reports/spatial/williams/monster-bash-1998.json`: sensors that sit inside a mechanism rather than on the playfield surface are projected onto that mechanism's own retained table object. The five Dracula position optos legitimately share one normalized coordinate because the figure rotates roughly 90 degrees about the vertical axis (the retained script sets `Drac.rotz = 77 - 1.125*(MechPos-5)`), not because it travels vertically, so five angular-position sensors have one playfield `x`/`y`. That is categorically different from the Centaur error below, where the projection was an arithmetic centroid of three *other* lamps. One retained `GIbot` member, `light11`, normalizes to `x = 1.087804` and was excluded as a table modelling anomaly rather than clamped, so GI address 0 carries 34 placements rather than 35.

Bally Centaur (`bally.centaur.1981`) is the project's first Bally MPU AS-2518-35 machine and introduced `controllers/pinmame/by35.json`, which every later BY35-driver machine should reuse. It was promoted to `author_ready` on 2026-08-06 and **demoted back to `partial` the same day**: an independent review caught that auxiliary lamp 113 carried the arithmetic centroid of three other lamps as a `validated` placement, and tracing that back uncovered a worse error described below. Every other dimension is validated; `coverage.missing` is exactly `["spatial_placement"]` and names one device.

Its profile rules: public momentary solenoid = PIA1:B selector + 1, so 1-15 with no address 16 because selector 15 is the idle state; four continuous outputs at 17-20; a six-column switch matrix published as sequential positions 1-48, not column-times-ten notation, with the three diagnostic contacts at -7 to -5; and a lamp strobe that ignores decoder selector value 0x0f, so 16, 32, 48, 64, 80, 96, 112 and 128 are unreachable decoder slots rather than unused lamps. The public lamp address collapses to `16 * d + lampadr + 1` on the main board, plus 64 on the auxiliary board.

Seven lessons from this machine generalise to every other BY35 game.

1. **A printed "Self Test #" column is a test order, not a public address.** The two are unrelated, and the ROM's own solenoid test publishes the mapping because it flashes each coil's number as it fires it - so run it rather than guessing. On Centaur that exposed printed 14 and 15 transposed against public 14 and 15, and public 7 being the outhole kicker rather than the ball release both retained scripts call it.
2. **On a six-column game one continuous solenoid address carries the sixth switch-column strobe, not a coil.** On Centaur that is public 17. It reads as permanently asserted because by35.c OR-accumulates solenoid state within each VBLANK window, so never read a held continuous output as an unused one.
3. **PinMAME reports lamp-matrix bits, not bulbs.** An unconnected matrix position still lights during a self-test lamp sequence. Distinguish them by what the ROM drives in normal play - the evidence schema now has `lamp_addresses_driven_outside_self_test` for exactly this.
4. **Check a community table for placeholder rows before trusting its geometry.** Centaur's retained table parks every auxiliary lamp its author could not place in a line along the bottom-left corner, and an earlier pass wrongly promoted those coordinates to validated placements.
5. **Board schematics are generic and may live in another game's manual - but look in your own manual first, and look properly.** The AS-2518-43 auxiliary lamp driver sheet is printed in the Centaur manual itself, on page 51 of the *Installation and General Game Operation Instructions*, with each J2 pin's lamp function annotated. An earlier pass concluded it was absent and fell back on the Kings of Steel schematics, which carry the same board without the per-pin functions; the result was that twelve lamp identities were assigned by playfield geometry instead of by tracing the board, and two of them came out backwards. Vendors list the board as fitted to Black Pyramid, Future Spa, Spy Hunter, Centaur, Kings of Steel, X's and O's, Centaur II and Kiss. Centaur is the only one PinMAME models with `lampCol > 0`, which makes the board look Centaur-specific from the emulator side and it is not.
6. **Trace the decoder-to-SCR-to-connector chain rather than matching lamps to playfield positions by eye.** On the AS-2518-43 each lamp data line enables one MC14555B decoder half - PD0 to U2A, PD1 to U2B, PD2 to U3A, PD3 to U3B - and the two latched address bits pick Q0, Q1 or Q2 of that half, with Q3 marked N/U on all four. That is why latched address 3 reaches no bulb, so public 68, 84, 100 and 116 are bare matrix positions. Doing this on Centaur reproduced nine of the retained table's twelve auxiliary assignments exactly and reversed two: the table binds its top *right* lane insert to public 65 and its top *left* to 97, while A9J2-7 reads TOP LEFT LANE and A9J2-18 reads TOP RIGHT LANE. Nine agreements are what make the two disagreements a table bug rather than a derivation fault. A cheap regression test - assert the left, middle and right lamps of a row have ascending x - would have caught it.
7. **A geometric projection is not an observation, and a centroid is the worst kind.** Lamp 113's withdrawn placement was the arithmetic centroid of the three top-lane inserts, which for three lamps in a row lands on top of the middle one. The placement schema has no field for declaring a projection, so the only honest way to record one is the `status` enum; anything that cannot reach `validated` on its own evidence blocks author-ready and should.

The one blocker is public lamp 113. It is a fitted auxiliary circuit - U3B output Q0 through SCR Q7 and resistor R15 to A9J2-11 - but it is the only one of the twelve whose function the factory schematic leaves blank, and the blank is deliberate: the genuinely unused pins beside it are marked N/U explicitly on the same sheet. Centaur has three top lanes, printed as switches 03, 04 and 05, so the tempting "fourth guardian rollover" reading has nothing behind it, and none of the four retained community tables from 2020 to 2025 models the address. Resolving it needs a Centaur playfield insert map that reaches A9J2-11, a photograph of an unrestored machine with the A9 harness visible, or a lamp test on real hardware. One other label is reasoned rather than printed and is documented as such in the knowledge note: option switches 17-20 come from the community option-switch documentation that all four retained tables carry, which agrees with the printed manual on every switch the manual does document.

The physical family is `centaur` (Bally, 1981) with `centaura` and `centaurb`, the 2004 and 2008 Bally/Oliver free-play ROMs, which are later firmware for the same physical machine rather than new games. Do not group `centauri`/`centaurj`, which are Inder's unrelated 1979 Spanish game and correctly remain a separate stub.

Bally Twilight Zone (`bally.twilight-zone.1993`) was curated on 2026-08-07 from a legacy-migrated `candidate`-only stub up to a `partial` record with every dimension except `semantic_naming` and `spatial_placement` validated. It introduced `controllers/pinmame/wpc-fliptronic.json` (`GEN_WPCFLIPTRON`, `PINMAME_HARDWARE_GEN_WPCFLIPTRON = 0x8`), the profile every earlier pre-WPC-95 Fliptronic-generation game (Addams Family 2/92 through the WPC-95 cutover) should reuse; the profile's most load-bearing fact is that this generation has **no** LPDC board, so unlike WPC-95 the range 37-44 is simply unused address space (`core_getSol` only serves that branch for `GEN_WPC95`/`GEN_WPC95DCS`/`GEN_ALLS11`) rather than a 37-40/41-44 duplicate pair. `coverage.missing` is `["spatial_placement", "unresolved_conflicts"]`; it carries one unresolved conflict, `conflict.clock-motor-direction-naming`, and six addresses (switches 26, 31-33, 45, 46, 55, and GI address 2) with no validated spatial placement because no VPX object binds them in the retained extraction.

Four things from it generalise.

1. **A retained manual scan can silently skip every even page in a run without announcing it.** This retained `Twilight_Zone_OPS.pdf` is missing printed pages 2-48, 2-50, 2-52, and 2-54 -- exactly the Switch Matrix, Solenoid/Flasher Table, and Lamp Matrix *wiring* pages, while every intervening odd "Locations" page survived. Detect this by checking that consecutive rendered pages' own printed page numbers increment by exactly one before trusting a "page not found" conclusion; do not assume a missing table simply wasn't printed.
2. **A driver's own `#define` variable names are not automatically correct, even when nothing else contradicts them at runtime.** `tz.c` names solenoid 56 `sClockFwd` and 57 `sClockRev`; the printed manual and the retained script's own commented-out cross-reference lines both read the opposite direction, and neither address is ever exercised at runtime (the mechanism's step table is inert behind an `#if 0` in this pinned revision), so there is no observation available to settle it. Two independently-agreeing external sources against one internal name is a real conflict, not a typo to silently prefer one side on.
3. **A manual's own auxiliary-board item numbers are not the public controller address, even on the same page as the addresses that are.** Twilight Zone's Solenoid/Flasher Locations page numbers its custom board 37-44 (probably the board's own silkscreen), which are genuinely public addresses 51-58; only the retained script's own bridging comments (`'(37)` next to `SolModCallback(51)`, etc.) resolve the mapping. Treat every printed item number as a `manual.address` alias and verify it against a script/source cross-reference before assuming it equals the binding.
4. **A legacy migrated label can be reversed even when it looks plausible.** The superseded stub labelled switch 34 "Right Slingshot" and 35 "Left Slingshot"; `tz.c`'s unambiguous `#define swLSling 34`/`#define swRSling 35`, the manual's own Switch Locations page, and the retained table's `Wall.LeftSlingShot`/`Wall.RightSlingShot` x-coordinates (0.296 and 0.676) all independently agree the legacy label had it backwards.
Bally Kiss (`bally.kiss.1979`) was promoted to `author_ready` on 2026-08-07 as the second Bally MPU AS-2518-35 machine, reusing `controllers/pinmame/by35.json` unchanged. It is the machine that turned the BY35 lamp chain from a Centaur-specific derivation into a reusable method, and four things from it generalise.

1. **The public solenoid address is the physical driver-board position, and it is stable across BY35 machines.** Kiss and Centaur both put the outhole kicker on public 7, the knocker on 6 and thumper bumpers on 9, 10 and 11. What differs between the two games is the printed Self Test # order, not the address, so the printed column stays a `manual.self-test` alias and never becomes the binding. Read the real mapping off the ROM: the manual itself says a number is flashed on the player score displays as each solenoid is pulsed.
2. **Whether a continuous output is a coil or a switch strobe depends on the column count.** Centaur is a six-column game, has to find a sixth strobe, and spends public 17 on it. Kiss has forty switches in five columns, needs no sixth strobe, and spends public 17 on the right outlane detour gate. The same address is a strobe on one BY35 game and a real coil on another; check the strobe block before deciding either way. Kiss's fourth continuous output, public 20, is genuinely unused and asserts only in the power-on pulse.
3. **Decoder-output-to-SCR is a board property and transfers between games, but the connector endpoint is not.** The AS-2518-23 fans several SCRs out to more than one connector branch, and which branch a harness plugs is game-specific. An earlier pass here reused Centaur's single-endpoint list, dropped eight Kiss lamps and had to be corrected, so always read the endpoint from the game's own lamp driver schematic. Public 43 is the clearest case: its SCR Q40 reaches both A5J2-9, marked N/U, and A5J3-22 "Same Player Shoots Again" on the block marked TO PLAYFIELD, so it is a real lamp and the retained table that modelled it was right. Kiss's split is 46 playfield-only, 7 lighting both a backglass socket and a playfield insert via Table B's panel-to-back-cab plug, 18 back box-only, 1 unused and 4 unpopulated - 76 addresses, being 60 main plus 16 auxiliary. That is 53 addresses feeding playfield lamps and the table models exactly 53 lamp objects; that exact agreement, not a hand-waved one, is what makes the derivation trustworthy.
4. **An auxiliary lamp board is not always there because the game ran out of lamps.** Kiss's main board still has a spare circuit. The A9 is fitted purely to animate the K-I-S-S letters on the backglass, which IPDB lists among the machine's notable features, so all twelve auxiliary circuits are back box devices with no playfield coordinate at all. A boot-and-play trace shows them switching in four groups of three, one group per letter.

Two evidence-handling notes worth carrying. The twelve A9J2 pin functions are not in the 57-page manual scan held here; they come from the Bally Kiss lamp chart as transcribed on PinWiki, a secondary source. It is trusted for those twelve because its own SCR-to-pin column reproduces the primary AS-2518-43 schematic exactly on all twelve circuits, because the runtime trace groups the circuits exactly as the chart implies, and because IPDB describes the same effect independently; every affected device note discloses it. Separately, IPDB is Cloudflare-gated and returns 403 to plain HTTP fetches and to headless Chrome, but a **headful** Puppeteer session with a persistent `userDataDir` clears the challenge in a couple of seconds - that is the working recipe for IPDB, VPU and VPF.

The physical family is the six production drivers `kiss`, `kissb`, `kissc`, `kissd`, `kisse` and `kissf`; the later five are Bally/Oliver seven-digit and free-play conversions of the same machine. Only `kiss` declares `lampCol = 8`, so it is the only driver through which PinMAME publishes the auxiliary addresses - an emulator modelling choice, not a hardware difference. **`kissp` and `kissp2` are deliberately excluded.** PinMAME declares them clones of `kiss`, but they live in `kissproto.c` on an Intel 8035, and IPDB records them as about eleven "New Technology" prototypes with blue vacuum-fluorescent displays, no speech and a three-board architecture that Bally itself called a completely different design. They keep the leftover `stub.pinmame.kiss` record, which is why the physical-game count rose to 786. A regression test asserts they never rejoin the production machine.

Bally The Addams Family (`bally.the-addams-family.1992`) was curated on 2026-08-07 as the second machine to reuse `controllers/pinmame/wpc-fliptronic.json` unchanged (`GEN_WPCFLIPTRON`). Unlike every prior Fliptronic/WPC-95 machine curated so far, its opto polarity sweep found **zero disagreement**: the manual's seven-address opto set (Bookcase Optos 1-4 at 53-56, Bumper Lane Opto at 57, Thing Down/Up Opto at 84/85, identified by a blank Switch Number plus a populated paired opto-assembly part number) matches `tafGameData`'s inverted-switch mask (`{0x00,0x00,0x00,0x00,0x00,0x7c,0x00,0x00,0x18,0x00,0x00,0x00}`) column for column and row for row, so `conflicts` is empty. Separately, seven "THING" name-chase header lamps (81-87) sit at a small negative normalized y in the retained table, just beyond the playfield's own top=0 edge, matching the manual's own Lamp Locations diagram drawing them above the cabinet outline; their y was clamped to the schema-valid boundary 0.000000 with the raw offset disclosed in the retained geometry dump, rather than either fabricating a coordinate or excluding seven real lamps.

Williams Indiana Jones: The Pinball Adventure (`williams.indiana-jones-the-pinball-adventure.1993`) was curated on 2026-08-07, replacing an existing legacy-migrated candidate-only partial record in place with a deterministic curator. It is a **wide-body "Superpin"** table: its retained VPWmod v1.0 table's own playfield bounds are `left=0 top=0 right=1093 bottom=2162`, so its `machine.playfield` block and every normalized coordinate use `x/1093`/`y/2162` rather than the `x/952`/`y/2162` divisor every other curated WPC game uses; using 952 here would have stretched every x coordinate by roughly 15% and silently corrupted the whole spatial set. It introduced `controllers/pinmame/wpc-dcs.json` (`GEN_WPCDCS`, `PINMAME_HARDWARE_GEN_WPCDCS = 0x10`) as a new profile rather than reusing `pinmame.wpc-fliptronic`: `GENWPC_HASFLIPTRON` does cover `GEN_WPCDCS`, so Fliptronic flipper-column behavior is identical, but WPC-DCS is a distinct pinned hardware-generation bit and the task explicitly called for deriving its own profile from source rather than reuse-by-analogy. Any future WPC-DCS game (`PINMAME_HARDWARE_GEN_WPCDCS`, roughly "Indiana Jones 10/93 - Popeye 3/94" per the pinned header comment) should reuse this profile unchanged. `coverage.missing` is `["polarity", "unresolved_conflicts"]`; it carries two unresolved conflicts and is otherwise complete across every dimension including spatial placement.

Seven things from it generalise.

1. **A driver-declared custom switch column's public address is not its schematic silkscreen number.** The 3-sw Opto PCB (idol) and Motor Opto Switch PCB (mini playfield) schematics both label their shared harness "switch column 9," printing public switches as 91-95. PinMAME's own fixed `CORE_CUSTSWCOL = CORE_STDSWCOLS = 12` places a driver's first declared custom switch column (`hw.swCol`) two columns past the Fliptronic column, so `wpc_m2sw` reports the same physical switches at public **121-128**. The retained script's own `Controller.Switch(121..125)` calls confirm the public binding directly; the printed "91-95" is captured only as a `manual.address` alias. Check this arithmetic explicitly on every future game that declares `hw.swCol` -- do not assume a printed "9th column" equals public 91-98.
2. **A driver-declared custom-solenoid board's own printed item numbers are not the public address either**, generalizing the lesson Twilight Zone already established for a different board. `ijGameData.hw.custSol = 7` publishes at `CORE_FIRSTCUSTSOL = 51` upward: the 8-Driver Board's own printed items 37-42 are public 51-56, confirmed exactly by the retained script's own `SolCallback`/`SolModCallback` comments and by the one named custom solenoid in the driver source (`sWheelMotor = CORE_CUSTSOLNO(6) = 56`, printed item 42 "Wheel Motor").
3. **Every would-be upper-flipper Fliptronic position can be repurposed, not just one.** Unlike Monster Bash (one repurposed position, F7) or Twilight Zone (none), Indiana Jones has no upper flippers at all and repurposes all four upper-flipper-adjacent positions: Fliptronic F5-F7 (public 115-117) are Center Drop Bank opto sensors and F8 (118) is a Left Ramp Made sensor, while the printed upper-flipper solenoid circuits 33-36 drive a right-ramp diverter and a "Top Lockup" post instead of any flipper. Check every WPC-DCS/Fliptronic game's Fliptronic block and printed solenoid circuits 33-36 individually; do not assume either range is flipper hardware by default.
4. **A manual can transpose two printed rows against its own switch matrix and against pinned PinMAME.** The Solenoid/Flasher Table prints solenoid 12 "Left Slingshot" and 13 "Right Slingshot," the opposite of the retained known-working script (`RandomSoundSlingshotRight`/`RandomSoundSlingshotLeft`) and of `ij.c`'s own `#define sRSling 12`/`#define sLSling 13` -- both of which independently agree with the unrelated, undisputed switch-side labels (switch 33 = Left = `swLSling`, switch 48 = Right = `swRSling`) and with the retained table's own geometrically-sided wall objects. Two independently-agreeing higher-priority sources against one manual row is enough to resolve a transposition outright (matching the Twilight Zone slingshot-naming precedent), not merely enough to flag a conflict.
5. **A manual can disagree with itself on the same fact.** The Switch Matrix page and the Switch Locations parts list disagree twice on this machine alone: the matrix page labels public 23 "Ticket Opto" (and `ij.c` even carries a vestigial `#define swTicketOpto 23` never referenced elsewhere in the driver) while the parts list prints item 23 blank with no part number -- the blank parts-list entry is physical-fitment ground truth, so 23 is `unused` despite two sources naming it. Separately, the Switch Locations page's own Left/Right Limit row for the mini-playfield tilt sensors (94/95) is reversed against both the Switch Matrix page and the driver's own `swLL_PoA`/`swRL_PoA` naming; majority evidence resolves it the other way. Check every printed table against its own sibling table on the same machine, not only against external sources.
6. **Opto polarity can be inconsistent within a single PinMAME inverted-switch-mask column.** Switch 71 (Captive Ball Front, opto per A-14231/A-14232) sits in the same mask column as normalized switches 72/73 (Mini Top/Bottom Hole, the identical opto part family) but is not itself normalized; switches 121-123 (Wheel Position 1-3, opto per the 3-sw Opto PCB) share one physical custom-column harness with normalized switches 124/125 (Mini Playfield Limits, opto per the Motor Opto Switch PCB) but are not themselves normalized. Two first-class conflicts (`conflict.captive-ball-front-opto-not-normalized`, `conflict.wheel-position-opto-not-normalized`) record this rather than assuming a whole column or a whole harness shares one polarity convention.
7. **A rotating-figure position sensor and a linear-mechanism limit sensor both project onto their own mechanism, not onto each other or onto a shared placeholder.** The idol wheel's three position optos (121-123) project onto the rotating idol figure's own table-object center (the same pattern Monster Bash's Dracula-position optos established), while the Path of Adventure's two limit optos (124/125) project onto the tilting mini-playfield assembly's own center -- a linear mechanism, not a rotating one, so it gets its own anchor rather than reusing the idol figure's. Separately, ten mini-playfield insert lamps (71-75, 81-85) share one raw local-space Primitive coordinate in the retained extraction because they are children of the tilting mini-playfield group; each was projected onto the playfield-fixed switch or trigger object at its own lane position instead of onto that shared, meaningless local coordinate.

The physical family is the fifteen-driver `ij` clone tree (`ij_l7` parent plus fourteen localization/display-fix/prototype clones). The unrelated Stern 2008 SAM-hardware `ij4_*` driver family (`CORE_GAMEDEF(ij4, 210, "Indiana Jones (V2.1)", 2009, "Stern", sam1, 0)`, `src/wpc/sam.c`) is a completely different physical machine that happens to share a PinMAME short-name prefix; it is untouched and needs its own curation pass under its own machine ID.

Williams Star Trek: The Next Generation (`williams.star-trek-the-next-generation.1993`) was curated on 2026-08-07, replacing an existing legacy-migrated candidate-only partial record in place with a deterministic curator, and is the second machine to reuse `controllers/pinmame/wpc-dcs.json` unchanged (confirmed from the pinned driver's own `GEN_WPCDCS` field rather than trusted from the task brief). Like Indiana Jones it is a **wide-body "Superpin" table** (`left=0 top=0 right=1093 bottom=2162`, so `x/1093`/`y/2162`). `coverage.missing` is exactly `["spatial_placement"]`; `conflicts` is empty and `coverage.dimensions.physical_wiring = "validated"` -- every printed opto shading (columns 3, 4, and row 1-7 of column 6) matches PinMAME's `sttngGameData` inverted-switch mask address for address, the first curated WPC-DCS/Fliptronic-generation game with zero polarity disagreements.

Three things from it generalise.

1. **A manual's own silkscreen numbering and a driver's own stale source comments can agree with each other while both being wrong about the runtime public address.** The switch matrix prints its custom column "column 9" (public 91-98) and the custom-solenoid board prints items 37-42; `sttng.c`'s own `CORE_CUSTSWNO`/`CORE_CUSTSOLNO` macro comments independently say the same numbers (`//92`, implying an older core.h). Both are wrong under the pinned revision: `CORE_CUSTSWCOL = CORE_STDSWCOLS = 12` and `CORE_FIRSTCUSTSOL = 51` place the true public addresses at 121-128 and 51-56. The retained known-working script settles it directly at runtime (`Controller.Switch(122/125/126/127)`, `SolCallBack(51..54)`), and independently, `core_getSol`'s `solNo<=44` branch returns constant 0 for `GEN_WPCDCS` before ever reaching `hw.getSol`, so the driver's own custom-solenoid handler could only ever be invoked above public address 50 -- a structural proof independent of any single source. Two agreeing "wrong" sources are not enough to overrule the arithmetic plus the runtime evidence.
2. **A "proximity sensor" is a real, distinct switch-construction category, not a synonym for opto.** Switches 16/17 (Left/Right Return Lane) are eddy-current proximity sensors (TDA0161 IC) per three independent sources (Section 3 schematic, switch-locations parts list with no LED/phototransistor pair, and PinMAME leaving their column uninverted) -- construction and polarity both agree with no conflict, but recording them as `switch_type: "opto"` would misdescribe the hardware. The schema's `switch_type` enum has no `proximity` value; use `other` and put the construction detail in `physical.notes`.
3. **A local-origin Primitive mesh is not a coordinate.** Three lamps (53 Advance in Rank, 85 Borg Lock, 86 Borg Jackpot) are modeled in the retained table as colored `Primitive` meshes sitting at `(0,0,0)`, parented to a transform this curation does not resolve, rather than as placeable `Light` objects. The canonical schema offers only `located` or `not_applicable` for a device's `spatial` field, with no `unresolved` status; the honest representation is to omit the `spatial` key entirely for these three devices (the pattern Bally Centaur's still-unresolved auxiliary lamp 113 already established) rather than inventing a status the schema does not define or a coordinate the evidence does not support.

The physical family is the nineteen-driver `sttng` clone tree (`sttng_l7` parent plus eighteen localization/LED-ghost-fix/prototype/community-mod clones); every driver is physically identical.

Bally Theatre of Magic (`bally.theatre-of-magic.1995`) was curated on 2026-08-07, replacing an existing legacy-migrated candidate-only stub in place, and is the first machine on this project to reuse `GEN_WPCSECURITY`; no existing controller profile matched it, so this curation introduced `controllers/pinmame/wpc-security.json`, derived entirely from pinned source (`GENWPC_HASWPC95` excludes `GEN_WPCSECURITY`, so it is electrically identical to WPC-DCS/WPC-Fliptronic -- no LPDC, freely repurposable Fliptronic upper-flipper circuits -- and its only generation-specific difference, `GENWPC_HASPIC`, changes the internal switch-column-select handshake, not the public address space). It also introduced the first unusually tall retained playfield on this project: the retained table's own bounds are `left=0 top=0 right=952 bottom=2594.1`, so its `machine.playfield` block and every normalized coordinate use `y/2594.1` rather than the `y/2162` divisor every other standard-height WPC game curated so far uses; using 2162 here would have compressed every y coordinate by roughly 20% and silently corrupted the whole spatial set. `coverage.missing` is `["unresolved_conflicts", "spatial_placement"]`; it carries one unresolved conflict and one address (GI string 5) with no VPX-bound coordinate, and its switch-matrix opto sweep found **zero disagreement** with pinned PinMAME (matching Bally The Addams Family and Bally Kiss).

Two things from it generalise.

1. **A retained table's own script can bind a non-production driver, and the fix is to verify -- not assume -- that the binding carries no electrical consequence.** The retained script reads `Const cGameName = "tom_14hb" '1.3x arcade rom - with credits`, but pinned `driver.c` dates `tom_14h`/`tom_14hb` "10/96 B" and comments them "Theatre of Magic (1.4 Home version)" -- a post-arcade-run software revision, not the shipped firmware, which is `tom_13` ("08/95 B", the clone-tree parent). Because every `tom_*` clone shares one `tomGameData`/`init_tom` pair through PinMAME's `CORE_CLONEDEF` macro, the driver registration itself structurally proves there is no controller-address or polarity difference between the bound driver and production, so no `conflicts` entry was needed for electrical semantics -- but this had to be verified from the driver source, not assumed from the ROM names looking similar. Separately, the retained script's own comments resolved two further manual-vs-manual disagreements about optional/prototype hardware (solenoid 19's motorized "Tiger Saw" captive-ball disc, commented `'****** VPM controlled (only in prototypes)` by the script's own author; solenoids 23/36's optional "Magic Post", gated behind a `CenterPost` toggle defaulting off) entirely in the manual's favor, without needing a harness trace.
2. **General illumination can carry the same script-vs-manual spatial conflict Tales of the Arabian Nights already established, on a cleaner printed table.** The manual's own Solenoid/Flasher Table wires GI strings 1-2 exclusively through Backbox connectors with `#555` bulbs and strings 3-5 exclusively through Playfield connectors with `#44` bulbs -- an internally consistent split with no ambiguity -- yet the retained script's `UpdateGI` drives genuine large playfield `Light` collections for strings 1-2 anyway as a stylized `Table1.ColorGradeImage` mood-lighting effect. The manual wins for spatial classification (`conflict.gi-strings-1-2-backbox-vs-script-playfield-binding`), keeping this record `partial`.

The physical family is the twelve-driver `tom` clone tree (`tom_13` parent plus eleven prototype/localization/ghost-fix/competition-mod/home-version clones); every driver is physically identical.

Bally Scared Stiff (`bally.scared-stiff.1996`) was curated on 2026-08-07, replacing an existing legacy-migrated candidate-only partial record in place, and is the fifth WPC-95 machine, reusing `controllers/pinmame/wpc-95.json` unchanged (confirmed directly from `ss.c` line 464's own `GEN_WPC95` field, not from the task brief). It covers the eight-driver `ss_15` clone tree (`ss_15` parent plus `ss_14`/`ss_12`/`ss_11`/`ss_11s10`/`ss_03`/`ss_01`/`ss_01b` firmware and prototype revisions), every one of which shares the one static `ssGameData` struct so all eight are physically identical. Its switch-matrix opto sweep found **zero disagreement** with pinned PinMAME: this manual's own opto-shading legend (a small box, "OPTO, TYPICALLY CLOSED") shades zero cells -- a genuine difference from Monster Bash's manual, which does shade its own optos this way -- so opto identity instead came from the Switch Locations parts list's two-row `(LED)` + `(Trans.)` construction disclosure, swept exhaustively across all 64 matrix positions. That sweep produced exactly the 17-address set (12, 31-38, 41-48) that `ssGameData`'s inverted-switch mask (`{0x00,0x02,0x00,0xff,0xff,0x00,0x00,0x00,0x00,0x00,0x00,0x00}`, indexed by column with bit = row-1) normalizes, matching Bally The Addams Family, Bally Kiss, and Williams Star Trek: The Next Generation's clean results. `coverage.missing` is `["output_semantics", "spatial_placement", "unresolved_conflicts"]`; it carries one unresolved conflict (`conflict.aux-lamp-column-fitment`, covering sixteen driver-declared auxiliary lamp addresses 91-98/101-108 that PinMAME's `hw.lampCol = 2` publishes but that the driver's own source comment calls a deleted prototype-only board while the retained production manual still prints their driving solenoids 37/38 as wired) and sixteen lamp addresses with no `spatial` key at all.

Three things from it generalise.

1. **A task brief's own mechanism framing can be wrong, and the fix is to report the correction rather than force the evidence to match it.** The brief that seeded this curation pass described "the motorised spinning Crate with a ball lock" and "the Boogie Men drop targets". Neither matches any primary source: the retained script's own `crate_pin_Hit` handler only wobbles a door a few degrees and back (no motor, no spin -- the machine's actual motorized, continuously rotating mechanism is a backbox Spider Wheel bonus selector driven by solenoids 39/40 and home switch 12, confirmed independently by both `ss.c`'s native `ss_wheelMech` and the script's own `cvpmMech` registration), and the four "Boogie Monster" figures the script names are pure nudge-reactive wobble props with **no** `Controller.Switch` or `SolCallback` binding anywhere in the file -- the real standup-target bank at switches 61-63 is a separate, unrelated feature printed "Three Bank Upper/Middle/Lower" on every source. Both corrections are recorded as fact in the promoted definition and knowledge note rather than silently reproducing the brief's framing.
2. **A driver's own source comment claiming hardware was deleted before production is not automatically correct, generalizing the lesson Star Trek: The Next Generation already established for stale macro comments.** `ss.c` declares `hw.lampCol = 2` (sixteen auxiliary lamp addresses) and says the matching 16-LED board "was not kept in production build", but the retained **production** manual (16-50048-101, September 1996, the shipped 1.5 ROM) still prints the two solenoids that clock this board's shift registers with real connectors and wire colors, not "NOT USED", and still lists the board itself on its Lower Playfield Parts page with no deleted/not-shown annotation. Neither source wins by fiat here: the retained known-working VPX table also implements no Light object at any of the sixteen addresses, and the sixteen-lamp "Web Award" ring the board's name suggests is already fully accounted for elsewhere on the ordinary matrix. Recorded as an unresolved first-class conflict rather than resolved either way.
3. **A manual can carry a genuine, badly garbled OCR text layer without being image-only, and the fix is unchanged: always render and read, never trust `pdftotext` alone.** Unlike Monster Bash's fully image-only scan (158 bytes of form feeds), this manual's `pdftotext -layout` output is substantial (hundreds of kilobytes) but its multi-column Section 2/3 tables come out scrambled beyond use -- the same failure mode already flagged for Tales of the Arabian Nights. Every printed table used in this definition was still read from 300-600 dpi renders and transcribed by hand.
