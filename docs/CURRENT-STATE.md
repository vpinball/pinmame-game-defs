## Identity and worktree integrity repair (2026-08-31)

The catalog-wide identity check now requires strict title-token equality (including physical-edition words such as EM, CE, SE, SS, prototype, signature, anniversary, remake, deluxe, and player-count variants, with `LE` normalized to `Limited` and only generic revision/modifier words removed), a manufacture year within one year when OPDB supplies one, and whole-token manufacturer compatibility before a definition may claim resolved OPDB identity. Every parenthetical qualifier in OPDB's canonical record name, except explicitly recognized free-play or firmware-revision metadata, must also appear in the machine title, so a generic `commonName` cannot erase an edition and an unclassified future qualifier fails closed. Word order alone is immaterial, while abbreviated, omitted-prototype, or split-edition titles require an explicit, machine-scoped override instead of passing through a single shared word. The importer independently compares both the canonical definition and the PinMAME root description with the selected OPDB record, rejects redundant overrides by replaying normal selection, and reports reviewed selections that confirm or waive a CSV choice as `csv_with_reviewed_override` rather than conflating them with replacements. A cross-manufacturer selection is accepted only when `config/opdb-overrides.json` names that exact record, records the reviewed reason, and links HTTPS evidence; name and manufacturer disagreements are tracked independently, so a simultaneous name mismatch cannot bypass the evidence requirement. The retained exceptions cite the Cirsa/Unidesa/Stargame manufacturer history and the serial-number record for Cosmic Princess's Australian production under license from Stern. The corrected crosswalk maps Game Plan Rio to `GrJy1-MDEbO` (IPDB 3523, 1978), Gottlieb Dragon to the solid-state `G4qPZ-ME0Nr` record (IPDB 729, 1978), Gottlieb Buck Rogers to `GRKx7-MJ49e` (IPDB 392, 1980), Mirco Spirit of 76 to `G4d0O-MJpj2` (IPDB 2294), and Playbar Cobra to the Playbar alias `G50zO-MJ97Z-AOvwl` (IPDB 4124). The Nutting Associates 1974 Flicker prototype has no matching record in the retained snapshot: its Bally 1975 mapping was removed, its canonical catalog identity is `nutting-associates.flicker-prototype.1974`, and `identity` is again honestly missing. OPDB regeneration now resolves 2,525 of 2,888 catalog drivers into 547 of 790 definitions across 495 families; 363 drivers and 243 definitions remain unmapped.

Shared-evidence discovery now uses `pinmame_game_defs.workspace.resolve_working_root`: it walks ancestors so it resolves both the primary checkout's sibling `pinmame-game-defs-working-dir` and arbitrarily deep checkouts below that working root, with an explicit `PINMAME_WORKING_ROOT` override for other layouts. The PinMAME attachment tool, promotion checker, excerpt re-renderer, and evidence-gated tests use that resolver. The promotion check no longer catches a missing retained OPDB snapshot and silently drops its identity-agreement checks: full `--check` fails closed, while explicit `--check-structure` lets bare CI verify all snapshot-independent invariants without claiming an evidence-backed identity check. Both modes now identify all 666 records by their durable promotion-note marker, including the 135 whose later platform attachment changed the original coverage template.

## VPX script candidate attachment (2026-08-29, sanitized 2026-08-30)

The VPX script extraction was regenerated with the official `extract-vpx` CLI so every evidence file and `reports/vpx-script-extraction.json` entry names current machine IDs, and `tools/attach_vpx_script_io.py` then attached the retained corpora's runtime I/O candidates to the partial definitions whose input and output arrays were still empty. After the 2026-08-31 identity repair made the retained Gottlieb 1980 Buck Rogers script eligible, 280 machines carried 13,210 candidate devices (switches, lamps, solenoids, and G.I. strings) drawn from 352 contributing scripts of the two pinned corpora; the 2026-09-25 Kingpin curation replaced that machine's 146 candidates from two scripts, leaving 279 machines, 13,064 devices and 350 scripts. Buck Rogers's six variable-target addresses retain their genuine numeric enumeration but use honest address-derived labels (`Switch 10` through `Switch 60`) because `VTSwitch` is a multi-address helper routine, not a physical device. The extraction treats both whole-line comments and quote-aware trailing comments as dead code (the Farfalla `Set Lamp 106` and Gottlieb Genesis template-boilerplate classes), and the label well-formedness guard rejected 2,027 raw VBScript fragments such as `Set Lamp 117,`. Per machine, scripts are merged in deterministic (corpus, path) order with first-wins deduplication per (group, address), each contributing script becomes a `vpx_script` source record carrying the corpus repository URI (deliberately without `/blob/`, so the pinned-script link table stays authoritative), the corpus revision, the script SHA-256, the corpus license (`NOASSERTION`), and its attribution. Machines with a declared controller platform keep only candidates whose group and address fall inside that platform profile's declared groups and address rules. Guardrails close the review blockers: VBScript event-handler symbols (`*_KeyDown`, `*_KeyUp`, `*_Init`, `*_Timer`, mouse equivalents) never become devices; every candidate must fall in public-address sanity bounds (switches/solenoids/lamps 1-128, G.I. 0-16); labels must be well-formed text (balanced parentheses, no trailing comma, no dotted method call, at least three characters), which rejected 2,027 raw VBScript fragments such as "Set Lamp 117,"; multi-address `*Switch` helper names fall back to address labels; and a script only contributes when its file path names the machine (every significant title token, including `prototype`, or the concatenated title appears as a path token, and a path carrying a model year the machine does not have is rejected), so re-theme tables that reuse a licensed-out ROM — `cGameName` matches the ROM, not the machine — stay leads in the extraction report instead of device sources; forty-four machines fed only by non-matching scripts or stripped of ill-formed labels reverted to identity-only records. `--dry-run` no longer writes knowledge notes. `--sanitize` recomputes every machine the pass has attached under the current rules and is deterministic, including rewriting knowledge headlines in either direction when the last attachment appears or disappears. Nothing is claimed: every enumeration requirement stays in `coverage.missing`, all devices stay `candidate`, and the knowledge notes state that a retained script outranks emulator-derived candidates for runtime semantics once curation weighs them — but each script must still be verified against the exact physical machine. Machines that already carried devices from the PinMAME define attachment or from curated work are untouched.

Five things generalise.

The first walks pressed the flippers by writing switches 5/6 directly, which PinMAME overwrites every frame (item 5), and roughly one press in ten registered twice; pressed through 84/82, every forward and backward lamp step lands on the next position, and the retained frames prove which positions each pass covered.

4. **The retained Kingpin table lineage is not a runtime authority.** All three corpus scripts are one lineage marked "Table not verified yet"; its captive-ball target pulses 49 instead of 32 and its right-ramp flasher routine sits on 23 instead of the ROM's 22. PinMAME's own Kingpin flasher typing (18-19, 21-31) was derived from that table and omits the backglass Big Al flasher at 20.

Placement stays open because no manual page lists G.I. sockets (2-41 marks every string `*NOT SHOWN*`) and the table renders all playfield G.I. from GI 2 through texture swaps and 18 ambience lights, so no bulb can be assigned to a string without guessing.
2. **Printed solenoid circuits normally reserved for upper flippers can drive plain, untranslated non-flipper devices with no address remapping at all**, a variant of the pattern Indiana Jones and Star Trek: TNG already established for *switch* columns. Printed circuits 33-36 ("Upr. Rt./Lt. Power/Hold") drive a playfield diverter gate and two independent devices (Vanish Magnet, Loop Post Diverter); because `totanGameData.hw.flippers` declares `FLIP_SOL(FLIP_L)` only (no `FLIP_UR`/`FLIP_UL` bit), pinned PinMAME's `core_getSol` never routes these four addresses through any flipper-coil path, so they pass straight through as public 33-36 with **no** translation -- unlike the lower-flipper pair, where printed 29-32 do translate to public 45-48 via `CORE_FIRSTLFLIPSOL`. Williams Monster Bash (`williams.monster-bash.1998`) was promoted on 2026-08-06 as the third WPC-95 machine and the first selected by Pinside Top 100 rank (it is rank 10 on the 2026-08-02 solid-state list), and **demoted back to `partial` the same day**: an independent review found that public switches 74-78 (Dracula Position 5-1) are printed normally-closed opto interrupters on the A-21402 Defender Switch Board Assembly, shaded "OPTO, TYPICALLY CLOSED" on the printed switch matrix like 31-36 and 42/43, but pinned PinMAME's `mbGameData` inverted-switch mask leaves column 7 at `0x00` and does not normalize them, while PinMAME's own `mb_mech[2]` table asserts them at their step ranges in what reads as the opposite sense. That asymmetry is now a first-class, unresolved `conflicts` entry (`conflict.dracula-position-opto-not-normalized`); `coverage.dimensions.physical_wiring = "conflicted"` and `coverage.missing = ["polarity", "unresolved_conflicts"]`. Resolving it needed a LibPinMAME gameplay-harness trace of a legal `mb_10`/`mb_106b` ROM observing the idle public state of 74-78 and their transitions as the Dracula motor steps through its 90-step range. **Re-promoted to `author_ready` on 2026-09-25:** hash-pinned runs of the ROM's own T.19 DRACULA service test (`evidence/runtime/wpc-95/monster-bash-dracula-service-test.json`) show that, with PinMAME's built-in Dracula mech enabled, every +/- press drives the motor, the next position switch rises to public level 1 in the order 78, 77, 76, 75, 74 and back, the ROM releases the motor at once, and its sensor display marks the matching box; with the Dracula feedback removed the boxes stay empty and the motor runs until the ROM's timeout. The public contract is level 1 at the sensed position with no consumer inversion, so the conflict was removed and every dimension is validated. It reuses `pinmame.wpc-95` unchanged and declares neither `custSol` nor `lampCol`, so it is otherwise the clean baseline for a WPC-95 game without auxiliary columns. Six things from it generalise.

1. **A same-titled arcade video game can masquerade as the manual.** Internet Archive items `monster_bash_schematics_ptm` and `monster_bash_ptm` are the 1982 Sega/Gremlin arcade video game, not the pinball machine: their sheets read `CPU BOARD 800-3278`, `2716 EPROM BOARD 800-3277`, `Video Board 800-3290`, `Sound Board 634-0316`. Render a page and check manufacturer and board part numbers before citing any manual. Late Williams manuals carry their own Section 3 wiring and schematics, so a separate schematics item is usually unnecessary.
2. **A WPC game can ship with no knocker.** Printed solenoid addresses 04 and 07 have populated power-driver transistors (Q67, Q69) but no voltage and no drive connection in the playfield, insert or cabinet columns, and no solenoid row anywhere uses the cabinet columns. PinMAME's `mb.c` still defines `#define sKnocker 7` and the retained script plays a knocker sound, because the WPC-95 OS pulses driver 7 as its standard knocker output. Record the address as enumerated-but-unfitted and cite all three sources; do not create the device. The blank-connection pattern, not the presence of a transistor, is what proves nothing is fitted.
3. **Fliptronic positions get repurposed for non-flipper devices.** F7, positionally the upper-left flipper EOS at public 117, is the Center Spinner. That is why `mbGameData` sets `FLIP_SW(FLIP_L|FLIP_U)` on a game with no upper flippers. Check the printed Fliptronic block on every WPC-95 game before assuming 111-118 are all flipper hardware.
4. **The printed flipper numbering is not the public address.** Manuals number the flipper circuits 29-36 as power/hold pairs, so printed 29/30 (lower right) is public 45/46 and printed 31/32 (lower left) is public 47/48, while printed 33-36 happen to equal public 33-36. Keep the printed numbers only as `manual.address` aliases.
5. **Scoped asterisks and the Cabinet columns both matter.** The footnote "these general illumination strings do not brighten and dim, they are always on" carries the asterisk on GI 04 and 05 only, so the three playfield strings do dim. GI 05 is also the one row on the page with a cabinet connection (J104-3 / J104-1), so the five printed strings split playfield / backbox insert panel / backbox-plus-cabinet and must not all be treated as playfield.
6. **Expect internal typos and resolve them by the symmetric partner.** The lamp matrix reads DRAC-ATTTACK, QUARTER MOOM, THREE-QUARTERS MOON and LEFT GARGOYLE where the parts list reads DRAC-ATTACK, QUARTER MOON, THREE-QUARTER MOON and LEFT GARGLE. Lamp 48 was settled by its partner insert 25, which reads RIGHT GARGLE on both pages; the Bride insert trio is PRIMP / WARM UP / GARGLE. Prefer the parts list for labels.

Its twelve documented projections are the same class Medieval Madness already established and are enumerated in `reports/spatial/williams/monster-bash-1998.json`: sensors that sit inside a mechanism rather than on the playfield surface are projected onto that mechanism's own retained table object. The five Dracula position optos legitimately share one normalized coordinate because the figure rotates roughly 90 degrees about the vertical axis (the retained script sets `Drac.rotz = 77 - 1.125*(MechPos-5)`), not because it travels vertically, so five angular-position sensors have one playfield `x`/`y`. That is categorically different from the Centaur error below, where the projection was an arithmetic centroid of three *other* lamps. One retained `GIbot` member, `light11`, normalizes to `x = 1.087804` and was excluded as a table modelling anomaly rather than clamped, so GI address 0 carries 34 placements rather than 35.

Bally Centaur (`bally.centaur.1981`) is the project's first Bally MPU AS-2518-35 machine and introduced `controllers/pinmame/by35.json`, which every later BY35-driver machine should reuse. It was promoted to `author_ready` on 2026-08-06 and **demoted back to `partial` the same day**: an independent review caught that auxiliary lamp 113 carried the arithmetic centroid of three other lamps as a `validated` placement, and tracing that back uncovered a worse error described below. Every other dimension is validated; `coverage.missing` is exactly `["spatial_placement"]` and names one device.

Its profile rules: public momentary solenoid = PIA1:B selector + 1, so 1-15 with no address 16 because selector 15 is the idle state; four continuous outputs at 17-20; a six-column switch matrix published as sequential positions 1-48, not column-times-ten notation, with the three diagnostic contacts at -7 to -5; and a lamp strobe that ignores decoder selector value 0x0f, so 16, 32, 48, 64, 80, 96, 112 and 128 are unreachable decoder slots rather than unused lamps. The public lamp address collapses to `16 * d + lampadr + 1` on the main board, plus 64 on the auxiliary board.

Seven lessons from this machine generalise to every other BY35 game.

1. **A printed "Self Test #" column is a test order, not a public address.** The two are unrelated, and the ROM's own solenoid test publishes the mapping because it flashes each coil's number as it fires it - so run it rather than guessing. On Centaur that exposed printed 14 and 15 transposed against public 14 and 15, and public 7 being the outhole kicker rather than the ball release both retained scripts call it.
2. **On a six-column game one continuous solenoid address carries the sixth switch-column strobe, not a coil.** On Centaur that is public 17. It reads as permanently asserted because by35.c OR-accumulates solenoid state within each VBLANK window, so never read a held continuous output as an unused one.
3. **PinMAME reports lamp-matrix bits, not bulbs.** An unconnected matrix position still lights during a self-test lamp sequence. Distinguish them by what the ROM drives in normal play - the evidence schema now has `lamp_addresses_driven_outside_self_test` for exactly this.
4. **Check a community table for placeholder rows before trusting its geometry.** Centaur's retained table parks every auxiliary lamp its author could not place in a line along the bottom-left corner, and an earlier pass wrongly promoted those coordinates to validated placements.
5. **Board schematics are generic and may live in another game's manual - but look in your own manual first, and look properly.** The AS-2518-43 auxiliary lamp driver sheet is printed in the Centaur manual itself, on page 51 of the *Installation and General Game Operation Instructions*, with each J2 pin's lamp function annotated. An earlier pass concluded it was absent and fell back on the Kings of Steel schematics, which carry the same board without the per-pin functions; the result was that twelve lamp identities were assigned by playfield geometry instead of by tracing the board, and two of them came out backwards. Vendors list the board as fitted to Black Pyramid, Future Spa, Spy Hunter, Centaur, Kings of Steel, X's and O's, Centaur II and Kiss. Centaur is the only one PinMAME models with `lampCol > 0`, which makes the board look Centaur-specific from the emulator side and it is not.
6. **Trace the decoder-to-SCR-to-connector chain rather than matching lamps to playfield positions by eye.** On the AS-2518-43 each lamp data line enables one MC14555B decoder half - PD0 to U2A, PD1 to U2B, PD2 to U3A, PD3 to U3B - and the two latched address bits pick Q0, Q1 or Q2 of that half, with Q3 marked N/U on all four. That is why latched address 3 reaches no bulb, so public 68, 84, 100 and 116 are bare matrix positions. Doing this on Centaur reproduced nine of the retained table's twelve auxiliary assignments exactly and reversed two: the table binds its top *right* lane insert to public 65 and its top *left* to 97, while A9J2-7 reads TOP LEFT LANE and A9J2-18 reads TOP RIGHT LANE. Nine agreements are what make the two disagreements a table bug rather than a derivation fault. A cheap regression test - assert the left, middle and right lamps of a row have ascending x - would have caught it.
7. **A geometric projection is not an observation, and a centroid is the worst kind.** Lamp 113's withdrawn placement was the arithmetic centroid of the three top-lane inserts, which for three lamps in a row lands on top of the middle one. The placement schema has no field for declaring a projection, so the only honest way to record one is the `status` enum; anything that cannot reach `validated` on its own evidence blocks author-ready and should.

The one blocker is public lamp 113. It is a fitted auxiliary circuit - U3B output Q0 through SCR Q7 and resistor R15 to A9J2-11 - but it is the only one of the twelve whose function the factory schematic leaves blank, and the blank is deliberate: the genuinely unused pins beside it are marked N/U explicitly on the same sheet. Centaur has three top lanes, printed as switches 03, 04 and 05, so the tempting "fourth guardian rollover" reading has nothing behind it, and none of the four retained community tables from 2020 to 2025 models the address. Resolving it needs a Centaur playfield insert map that reaches A9J2-11, a photograph of an unrestored machine with the A9 harness visible, or a lamp test on real hardware. One other label is reasoned rather than printed and is documented as such in the knowledge note: option switches 17-20 come from the community option-switch documentation that all four retained tables carry, which agrees with the printed manual on every switch the manual does document.

The physical family is `centaur` (Bally, 1981) with `centaura` and `centaurb`, the 2004 and 2008 Bally/Oliver free-play ROMs, which are later firmware for the same physical machine rather than new games. Do not group `centauri`/`centaurj`, which are Inder's unrelated 1979 Spanish game and correctly remain a separate stub.

Four things from it generalise.

1. **A retained manual scan can silently skip every even page without announcing it.** This retained `Twilight_Zone_OPS.pdf` carries only odd-numbered printed pages throughout (checked against the printed footers: PDF 40 = 2-9, 41 = 2-11, 56 = 2-41, 57 = 2-43, 58 = 2-45, 64 = 2-57), so every even page is absent -- among them the Switch Matrix, Solenoid/Flasher Table, and Lamp Matrix *wiring* pages 2-50, 2-52 and 2-54 and the Upper Playfield Parts list that belongs with the page 2-49 drawing, while every odd "Locations" page survived. The retained external `manual-transcription.md` still claims only the narrower 2-48 to 2-54 gap and records an older manual SHA-256 (`a1df4b4a...`); the curator pins the actual file (`66b657fd...`), and the transcription's header is stale on both points. Detect this by checking that consecutive rendered pages' own printed page numbers increment by exactly one before trusting a "page not found" conclusion; do not assume a missing table simply wasn't printed.
2. **A driver's own `#define` variable names are not automatically correct, even when nothing else contradicts them at runtime.** `tz.c` names solenoid 56 `sClockFwd` and 57 `sClockRev`; the printed manual and the retained script's own commented-out cross-reference lines both read the opposite direction, and neither address is ever exercised at runtime (the mechanism's step table is inert behind an `#if 0` in this pinned revision), so there is no observation available to settle it. Two independently-agreeing external sources against one internal name is a real conflict, not a typo to silently prefer one side on.
3. **A manual's own auxiliary-board item numbers are not the public controller address, even on the same page as the addresses that are.** Twilight Zone's Solenoid/Flasher Locations page numbers its custom board 37-44 (probably the board's own silkscreen), which are genuinely public addresses 51-58; only the retained script's own bridging comments (`'(37)` next to `SolModCallback(51)`, etc.) resolve the mapping. Treat every printed item number as a `manual.address` alias and verify it against a script/source cross-reference before assuming it equals the binding.
4. **A legacy migrated label can be reversed even when it looks plausible.** The superseded stub labelled switch 34 "Right Slingshot" and 35 "Left Slingshot"; `tz.c`'s unambiguous `#define swLSling 34`/`#define swRSling 35`, the manual's own Switch Locations page, and the retained table's `Wall.LeftSlingShot`/`Wall.RightSlingShot` x-coordinates (0.296 and 0.676) all independently agree the legacy label had it backwards.
Bally Kiss (`bally.kiss.1979`) was promoted to `author_ready` on 2026-08-07 as the second Bally MPU AS-2518-35 machine, reusing `controllers/pinmame/by35.json` unchanged. It is the machine that turned the BY35 lamp chain from a Centaur-specific derivation into a reusable method, and four things from it generalise.

1. **The public solenoid address is the physical driver-board position, and it is stable across BY35 machines.** Kiss and Centaur both put the outhole kicker on public 7, the knocker on 6 and thumper bumpers on 9, 10 and 11. What differs between the two games is the printed Self Test # order, not the address, so the printed column stays a `manual.self-test` alias and never becomes the binding. Read the real mapping off the ROM: the manual itself says a number is flashed on the player score displays as each solenoid is pulsed.
2. **Whether a continuous output is a coil or a switch strobe depends on the column count.** Centaur is a six-column game, has to find a sixth strobe, and spends public 17 on it. Kiss has forty switches in five columns, needs no sixth strobe, and spends public 17 on the right outlane detour gate. The same address is a strobe on one BY35 game and a real coil on another; check the strobe block before deciding either way. Kiss's fourth continuous output, public 20, is genuinely unused and asserts only in the power-on pulse.
3. **Decoder-output-to-SCR is a board property and transfers between games, but the connector endpoint is not.** The AS-2518-23 fans several SCRs out to more than one connector branch, and which branch a harness plugs is game-specific. An earlier pass here reused Centaur's single-endpoint list, dropped eight Kiss lamps and had to be corrected, so always read the endpoint from the game's own lamp driver schematic. Public 43 is the clearest case: its SCR Q40 reaches both A5J2-9, marked N/U, and A5J3-22 "Same Player Shoots Again" on the block marked TO PLAYFIELD, so it is a real lamp and the retained table that modelled it was right. Kiss's split is 46 playfield-only, 7 lighting both a backglass socket and a playfield insert via Table B's panel-to-back-cab plug, 18 back box-only, 1 unused and 4 unpopulated - 76 addresses, being 60 main plus 16 auxiliary. That is 53 addresses feeding playfield lamps and the table models exactly 53 lamp objects; that exact agreement, not a hand-waved one, is what makes the derivation trustworthy.
4. **An auxiliary lamp board is not always there because the game ran out of lamps.** Kiss's main board still has a spare circuit. The A9 is fitted purely to animate the K-I-S-S letters on the backglass, which IPDB lists among the machine's notable features, so all twelve auxiliary circuits are back box devices with no playfield coordinate at all. A boot-and-play trace shows them switching in four groups of three, one group per letter.

Two evidence-handling notes worth carrying. The twelve A9J2 pin functions are not in the 57-page manual scan held here; they come from the Bally Kiss lamp chart as transcribed on PinWiki, a secondary source. It is trusted for those twelve because its own SCR-to-pin column reproduces the primary AS-2518-43 schematic exactly on all twelve circuits, because the runtime trace groups the circuits exactly as the chart implies, and because IPDB describes the same effect independently; every affected device note discloses it. Separately, IPDB is Cloudflare-gated and returns 403 to plain HTTP fetches and to headless Chrome, but a **headful** Puppeteer session with a persistent `userDataDir` clears the challenge in a couple of seconds - that is the working recipe for IPDB, VPU and VPF.

The physical family is the six production drivers `kiss`, `kissb`, `kissc`, `kissd`, `kisse` and `kissf`; the later five are Bally/Oliver seven-digit and free-play conversions of the same machine. Only `kiss` declares `lampCol = 8`, so it is the only driver through which PinMAME publishes the auxiliary addresses - an emulator modelling choice, not a hardware difference. **`kissp` and `kissp2` are deliberately excluded.** PinMAME declares them clones of `kiss`, but they live in `kissproto.c` on an Intel 8035, and IPDB records them as about eleven "New Technology" prototypes with blue vacuum-fluorescent displays, no speech and a three-board architecture that Bally itself called a completely different design. They keep the leftover `stub.pinmame.kiss` record, which is why the physical-game count rose to 786. A regression test asserts they never rejoin the production machine.

Seven things from it generalise.

1. **A driver-declared custom switch column's public address is not its schematic silkscreen number.** The 3-sw Opto PCB (idol) and Motor Opto Switch PCB (mini playfield) schematics both label their shared harness "switch column 9," printing public switches as 91-95. PinMAME's own fixed `CORE_CUSTSWCOL = CORE_STDSWCOLS = 12` places a driver's first declared custom switch column (`hw.swCol`) two columns past the Fliptronic column, so `wpc_m2sw` reports the same physical switches at public **121-128**. The retained script's own `Controller.Switch(121..125)` calls confirm the public binding directly; the printed "91-95" is captured only as a `manual.address` alias. Check this arithmetic explicitly on every future game that declares `hw.swCol` -- do not assume a printed "9th column" equals public 91-98.
2. **A driver-declared custom-solenoid board's own printed item numbers are not the public address either**, generalizing the lesson Twilight Zone already established for a different board. `ijGameData.hw.custSol = 7` publishes at `CORE_FIRSTCUSTSOL = 51` upward: the 8-Driver Board's own printed items 37-42 are public 51-56, confirmed exactly by the retained script's own `SolCallback`/`SolModCallback` comments and by the one named custom solenoid in the driver source (`sWheelMotor = CORE_CUSTSOLNO(6) = 56`, printed item 42 "Wheel Motor").
3. **Every would-be upper-flipper Fliptronic position can be repurposed, not just one.** Unlike Monster Bash (one repurposed position, F7) or Twilight Zone (none), Indiana Jones has no upper flippers at all and repurposes all four upper-flipper-adjacent positions: Fliptronic F5-F7 (public 115-117) are Center Drop Bank opto sensors and F8 (118) is a Left Ramp Made sensor, while the printed upper-flipper solenoid circuits 33-36 drive a right-ramp diverter and a "Top Lockup" post instead of any flipper. Check every WPC-DCS/Fliptronic game's Fliptronic block and printed solenoid circuits 33-36 individually; do not assume either range is flipper hardware by default.
4. **A manual can transpose two printed rows against its own switch matrix and against pinned PinMAME.** The Solenoid/Flasher Table prints solenoid 12 "Left Slingshot" and 13 "Right Slingshot," the opposite of the retained known-working script (`RandomSoundSlingshotRight`/`RandomSoundSlingshotLeft`) and of `ij.c`'s own `#define sRSling 12`/`#define sLSling 13` -- both of which independently agree with the unrelated, undisputed switch-side labels (switch 33 = Left = `swLSling`, switch 48 = Right = `swRSling`) and with the retained table's own geometrically-sided wall objects. Two independently-agreeing higher-priority sources against one manual row is enough to resolve a transposition outright (matching the Twilight Zone slingshot-naming precedent), not merely enough to flag a conflict.
5. **A manual can disagree with itself on the same fact.** The Switch Matrix page and the Switch Locations parts list disagree twice on this machine alone: the matrix page labels public 23 "Ticket Opto" (and `ij.c` even carries a vestigial `#define swTicketOpto 23` never referenced elsewhere in the driver) while the parts list prints item 23 blank with no part number -- the blank parts-list entry is physical-fitment ground truth, so 23 is `unused` despite two sources naming it. Separately, the Switch Locations page's own Left/Right Limit row for the mini-playfield tilt sensors (94/95) is reversed against both the Switch Matrix page and the driver's own `swLL_PoA`/`swRL_PoA` naming; majority evidence resolves it the other way. Check every printed table against its own sibling table on the same machine, not only against external sources.
6. **Opto polarity can be inconsistent within a single PinMAME inverted-switch-mask column.** Switch 71 (Captive Ball Front, opto per A-14231/A-14232) sits in the same mask column as normalized switches 72/73 (Mini Top/Bottom Hole, the identical opto part family) but is not itself normalized; switches 121-123 (Wheel Position 1-3, opto per the 3-sw Opto PCB) share one physical custom-column harness with normalized switches 124/125 (Mini Playfield Limits, opto per the Motor Opto Switch PCB) but are not themselves normalized. Both were first recorded as conflicts (`conflict.captive-ball-front-opto-not-normalized`, `conflict.wheel-position-opto-not-normalized`) rather than assuming a whole column or harness shares one polarity convention, and on 2026-09-25 the ROM's own service tests settled both: the unnormalized public levels are what the ROM expects. PinMAME's mask follows the ROM's own reading of each switch, not the printed construction, so an unnormalized printed opto is not by itself a polarity error.
7. **A rotating-figure position sensor and a linear-mechanism limit sensor both project onto their own mechanism, not onto each other or onto a shared placeholder.** The idol wheel's three position optos (121-123) project onto the rotating idol figure's own table-object center (the same pattern Monster Bash's Dracula-position optos established), while the Path of Adventure's two limit optos (124/125) project onto the tilting mini-playfield assembly's own center -- a linear mechanism, not a rotating one, so it gets its own anchor rather than reusing the idol figure's. Four things from it generalise.

1. **A driver's own generic mirror code can silently duplicate an unrelated device's state under a flipper-shaped name.** `capcom.c`'s `io_w` unconditionally mirrors physical solenoid addresses 9/10/11/12 into synthetic addresses 45/47/33/35 assuming those four are always "the four flipper circuits" -- true for Big Bang Bar's Left/Right/Upper-Right flippers at 9/10/11, but address 12 is Eject Hole (confirmed identically by the manual and the schematic device table), not an upper-left flipper. 2. **A driver's own admitted naming defect can make the emulator's constant names actively misleading for a specific game's left/right sense.** The same mirror code writes physical address 9 (S9, "L. Flipper") into `sLRFlipPow`=45 and physical address 10 (S10, "R. Flipper") into `sLLFlipPow`=47 -- the opposite left/right sense from PinMAME's own constant names -- and the driver's own source comment admits the mapping "does not correspond to manuals or any other reference." For Big Bang Bar's two ramp diverters, the rotating gate-arm object and its companion drop-wall panel object(s) -- manipulated together in one `Sub` by the retained script -- sit at opposite ends of the playfield in the raw extraction. 1. **Data East runs on the shared Williams System 11 core, and there is no `de.c`.** `degames.c` includes `s11.h`, and `s11.c` installs no `MDRV_SWITCH_CONV` or `MDRV_LAMP_CONV` of its own, so it inherits PinMAME's sequential defaults at `core.c:3987-3988`. **Both matrices are column-major**: address = (column - 1) x 8 + row, confirmed cell by cell against this machine's own printed charts. 2. **There is no GI channel on this platform at all.** `coreGlobals.nGI` is never assigned anywhere in `s11.c` and `gi[]` is never written, so `vp_getGI` always reports zero. 3. **Public solenoid 10 is a relay that re-routes addresses.** With it energised, `s11.c:564-574` re-publishes outputs 1-8 at 25-32 and reads zero at 1-8. Since the game declares no `FLIP_SOL`, no `FLIP_EOS` bit is ever set and the EOS simulation at `core.c:1756-1775` never runs, so end-of-stroke is not modelled at all. **A recreation must not drive 15 or 16**; `core_updateSw` overwrites them every frame, and the retained known-working script indeed never touches either. Check `FLIP_SWNO` against the printed matrix on every non-Fliptronic game rather than assuming the macro names buttons.
5. **A retained table defined by drag points has no center, and a centroid is not a measurement.** Point-like objects (Light, Trigger, Kicker, Bumper, Flasher, Primitive) carry their own center; extended objects (Wall, Ramp, Rubber) carry only `drag_points`. Its playfield is a further instance of the divisor trap: the retained table's own bounds are `left=0 top=0 right=952 bottom=1974`, so every y normalizes by **1974**, not the 2162 most WPC-era tables use — using 2162 would have compressed every coordinate by about nine percent. Six things from it generalise.

1. **`sxx.ssSw` is the System 11 special-solenoid-to-switch map, it is indexed sequentially, and it is a free independent check on a manual's own Special # column.** High Speed is the first curated machine whose driver populates it (`49,50,35,34,33,0`, the trailing six `INITGAMEFULL` arguments). The VBLANK loop at `src/wpc/s11.c` lines 191-200 indexes `CORE_FIRSTSSSOL + ii` directly with `ii = 0..5` against `ssSw[ii]` and **not** through `setSSSol`'s scrambled `ssSolNo` table, so `ssSw[0]` drives public solenoid 17 and `ssSw[5]` drives 22; a zero entry means "not switch-driven" and is skipped. It models real switched-solenoid hardware, where the actuating switch completes the coil circuit itself and the CPU only gates the supply through the enable. On this machine it matched the manual's Solenoid Table on all five populated slots (17/Left Kicker/switch 49, 18/Right Kicker/50, 19/Right Jet Bumper/35, 20/Lower Left Jet Bumper/34, 21/Upper Left Jet Bumper/33), and the one slot left at zero is the one special solenoid that is a flasher rather than a kicker or bumper. `system-11.json` needed no change: the profile already describes 17-22 correctly and already lists `sxx.ssSw` among the `core.h` fields it derives from, and the mapping itself is game-specific data, not a platform address rule -- the same reason the profile declines to fix GI addresses.

Six things from it generalise.

1. **The fifth `INITGAME`/`INITGAME2` argument in `by35games.c` is the auxiliary lamp-column count, not a switch-column count.** The macro expands to `core_tGameData {gen, disp, {flip, 0, lamps, 0, sb, db, ...}}` and `core_tGameData.hw` is declared `{flippers, swCol, lampCol, custSol, ...}`, so it passes a literal `0` for `swCol` and the argument for `lampCol`. The task brief that seeded this curation read it as a switch-column count and derived a rule from that, which is wrong and is recorded here as a correction rather than reproduced. Six columns and forty-eight matrix positions is the platform ceiling regardless of the driver declaration, and how many a game wires is a property of its own harness.
2. **Which continuous solenoid address carries the sixth switch-column strobe differs per game and must be read from three places, not inherited.** Centaur spends public 17 on it, Kiss (a five-column game) spends 17 on a real coil, and Fathom spends public **20**: its playfield wiring diagram takes `ST 5` from `A4J4-8`, that is the PIA1:B PB7 line, `by35.c`'s default non-`BY35GD_SWVECTOR` path reads exactly `(locals.b1 & 0x80) >> 2` for the sixth column, and `src/lisy/lisy35.c`'s `lisy35_set_variant` **case 3, commented `//Fathom`**, sets `lisy35_J4PIN8_is_strobe` and masks that bit out of the coil data with `cont_data &= 0x07`. A boot-only harness run then shows address 20 asserted continuously from the moment the game comes up. Check `lisy35_set_variant` for the game by name: it is a per-game table of exactly this fact.
3. **The ROM's own solenoid self test resolves the whole printed-number-to-public-address mapping in one harness run, and it needs the right boot wait.** Pulsing the Self Test contact (-7) three times *after* the power-up test has finished (18 s on this ROM; earlier presses land during power-up and do nothing) reaches the solenoid test, whose twenty-one-pulse cycle repeats in exact printed order. 1. **No Stern S.A.M. game in the pinned source ever populates `wpc.invSw`**, exactly as no Whitestar game does. `sam.c`'s `INITGAME` macro expands to a positional aggregate initializer that stops at the `hw` sub-struct, leaving the trailing `wpc`/`simData`/`sxx` members at their C zero-initialization default, and `core.c` copies those zeros straight into the live switch-inversion mask; searching the whole of `src/wpc/sam.c` for `invSw` returns no assignment anywhere. 3. **`hw.custSol = 16` is a macro constant, not a per-game decision.** Every S.A.M. game enumerates public solenoids 51-66 and always reports `nSolenoids = 66`, whatever auxiliary hardware is fitted. What differs is `gameSpecific1`, which selects which of `sam.c`'s six auxiliary write paths is enabled; Pirates declares `SAM_NO_AUX`, so nothing ever writes those sixteen outputs and the manual prints no coil beyond `#32`. 4. **The start button lives inside the playfield switch-matrix address range.** `SAM_COMPORTS` puts Start on internal switch column 2 bit 7 and Tournament Start on bit 6, which `core_swSeq2m`'s `no + 7` conversion places at public 16 and 15; this manual independently prints `SW. #15 TOURNAMENT START` and `SW. #16 START BUTTON` with a black `CABINET` tag. 6. **Three printed names plus three retained positions can settle a left/right question the runtime script gets wrong.** The manual names the three pop bumpers LEFT, RIGHT and BOTTOM on both its switch page (30/31/32) and its coil page (9/10/11), and its Coil Locations plan draws the three coil callouts at the cluster's left, right and player-nearest positions in that order; the retained script binds its three Bumper objects to 30/31/32 in naive numeric order instead, which makes its LEFT bumper the player-nearest one. Two further conflicts are game-specific rather than platform-wide. `conflict.flasher-back-panel-bulb-count`: the Coil and Flash Lamp Locations page draws one solenoid-22 and one solenoid-30 callout inside its back-panel inset, which makes both printed quantities add up, while printed page 91 lists exactly two `#89` sockets on the back panel and labels both of them `Q22 FLASH` with no `Q30` socket anywhere. Six things from it generalise.

1. **A lamp binding can use `vpmMapLights` rather than `Lampz`, and a resolver written for one finds nothing in the other while reporting a clean result.** This table sets each light's own `TimerInterval` to its ROM lamp index and collects them in `AllLamps`; the Batman-era resolver, which parses `Lampz.MassAssign`, found **zero** lamps here and produced a successful-looking run. 2. **One lamp address can drive two bulbs at genuinely different playfield positions.** Addresses 7, 9, 18 and 27 each carry two; lamp 18's pair sits at x=64.6 and x=808.4, opposite sides of the table. 3. **A shared platform macro's label can match no machine that uses it.** `s11.h`'s `DE_COMPORTS` names dedicated column-1 position 2 "Ball Tilt". 6. **A claim about what the retained script does is a testable fact, and must be tested against the script.** This record carried the sentence "The retained known-working VPW 2.0 script indeed never touches 15 or 16" through three audit rounds and 52 passing tests. It is false - VPW 2.0 drives both from the cabinet flipper key at `script.vbs:928-929` and `960-961`. The sentence was inherited from the Data East Batman record, where it is **true**: that table's VPW 1.1 script really does leave those addresses alone. So this is the carryover failure mode in its purest form - a correct sentence copied to a machine where it is wrong, surviving because prose about evidence was never compared against the evidence. A blind independent re-derivation of the whole address model found it; the re-derivation agreed with this record on every one of the 66 switch dispositions, all 64 lamps and all 34 enumerated drives, so the disagreement it did produce was worth acting on. The fix is a gate, not a correction. `test_no_prose_claims_the_script_avoids_an_address_it_actually_drives` checks every device note **and the knowledge note** against the set of addresses the retained script really asserts, and proves it is not inert by first running itself against the four historical wordings that shipped and were wrong. Three things about that gate are worth carrying to the next machine. It runs from a pinned address set rather than from the script, because CI supplies no evidence root and a gate that only runs on the curator's machine is not a gate; a second, evidence-enabled test rechecks the pinned set against the script whenever the evidence is present. The address scan is case-insensitive, because this script writes `Controller.switch(31)` in lower case and a case-sensitive scan silently missed it. A first attempt at this gate got two of those three wrong.

1. **A shared source file does not make Data East a Williams System 11 controller.** `GEN_DE` has its own Data East generation bit and initialization path. ## Conflict hygiene pass (2026-08-05)

A review of every `conflicts` record carrying no resolution path found that 138 of 164 gave a future curator no way to start. 31 of those were not disagreements about a physical machine at all, and are removed; the rule that produced them is fixed at source, and `docs/INSTRUCTIONS.md` now carries the standard under **What is not a conflict**.

`import-legacy` compared a platform record's generic cabinet label against a game record's own label for the same address and emitted a conflict whenever the two strings differed, with no notion of whether they named the same device: `ROM Started` against `Game On Relay`, `Coin Button 1` against `Coin 1`, `Lower Right Flipper` against `Right Flipper`. `legacy.py` now applies `_names_one_device` before emitting anything, so a re-import cannot recreate them. The pairs naming genuinely different devices — `Ball Roll Tilt` against `Drop Target 2`, `Coin Button 1` against `Backbox Basket Score 1`, `Coin Button 3` against `Right Coin Chute` — are untouched and remain first-class conflicts.

That helper is deliberately conservative, because a false positive deletes a real disagreement silently while a false negative only leaves a record someone can close later. Two defects in its first draft, both caught before merge and both now pinned by `tests/test_legacy_label_synonyms.py`: side words are stripped as qualifiers, so `Upper Left Flipper` and `Upper Right Flipper` merged on core equality until the side test was moved ahead of it; and an unrestricted subset rule plus `relay`/`solenoid` in the noise list merged `Right Flipper Button` with `Right Flipper EOS` and `Start Button` with `Start Relay`. Equivalence beyond exact equality is now an explicitly written-out pair, and a device-class word is never noise.

**The flipper end-of-stroke records were kept, and are now marked `status: "ignored"`.** They are not authoring-relevant — an EOS contact exists so a physical coil's power winding is cut before it burns, a recreation has no coil, and these platforms model no EOS at all, since the driver macro sets `FLIP_SWNO` without `FLIP_SOL` so `core.c`'s EOS simulation never runs and PinMAME publishes cabinet-button state at the address instead — but the affected addresses carry `provenance.status = "conflicted"`, and deleting the record that explains it leaves an assertion no reader can account for. Deletion and blocking were both wrong answers, so the schema gained a third: a conflict may carry `status: "ignored"` plus a `rationale` saying why the answer cannot reach a recreation. Ten such records across the five Data East machines are marked that way. The adjacent `synthetic-flipper-public-state` records are deliberately **not**: which physical winding each fabricated `45-48` state corresponds to is a real unresolved question, and they stay first-class.

The state is defined so it cannot be acquired by accident. An absent `status` means unresolved, never the reverse. A `rationale` is required whenever `status` is `ignored`, and it must contain an **ASCII** letter or digit. Three weaker rules were each tried and each let through a reason that renders as nothing: `minLength: 1` accepts a single space; a non-whitespace test accepts U+200B and every other invisible Unicode does not classify as whitespace; and `str.isalnum()` accepts default-ignorable *letters* such as U+115F HANGUL CHOSEONG FILLER. ASCII rather than a Unicode class is deliberate — the schema states the same rule as a `pattern`, JSON Schema specifies ECMA-262 semantics, and `\W` is Unicode-aware in Python but ASCII-only in ECMAScript, so a Unicode-class rule would mean two different things depending on which validator ran it. `unresolved_conflicts()` in `validation.py` is the single place the author-ready gate, the coverage-consistency rule and the generated blocker reports all consult; the three Data East curators that emit an `unresolved_conflicts` blocker import it rather than restating the predicate, because the first draft did restate it and the copy immediately fell behind when the real rule started demanding a rationale. And a definition may not list `unresolved_conflicts` in `coverage.missing` when every conflict it holds is ignored. `tests/test_ignored_conflicts.py` pins all four, and each guard is mutation-checked: deleting the coverage rule, the author-ready gate, the rationale requirement, or narrowing it to letters-only at either the runtime or the schema layer all fail the suite rather than passing because today's files happen to be consistent.

No completion score moved in this pass, because all five affected definitions still carry unresolved conflicts of their own and so keep `unresolved_conflicts` in `coverage.missing`; the mechanism is what changed, not the arithmetic. The catalog holds 133 conflicts against 164 before the pass — 123 unresolved and 10 ignored — across 13 touched definitions and seeds. `tools/prune_nonconflicts.py` clears the already-committed label records using `legacy.py`'s own function rather than a second copy of the rule, and has a `--check` mode.

**That gap is now closed.** The `coverage.missing` rule originally ran one way only: a definition could not claim `unresolved_conflicts` without holding one, but it could hold one and omit the requirement, which overstated its completion score. Eighteen definitions did exactly that. Both producers are fixed at source rather than the records patched: `import-legacy` wrote the fixed `MIGRATION_MISSING` list whatever conflicts it had just emitted, which accounts for fourteen, and `fail_closed_spatial_partial()` appended only `spatial_placement` when it downgraded an author-ready definition to partial, which accounts for the other four — that definition was written as author-ready, where an unresolved conflict cannot exist, so its `missing` list had no reason to mention one, and demoting it makes that list load-bearing again. `curate_avatar_pro_spatial.py` also attached its conflicts *after* the downgrade, so even the fixed helper could not see them. The validator now requires the two to agree in both directions and the new half is mutation-checked. Fourteen definitions fell 19 to 13 and four fell 94 to 88; the catalog-wide count of definitions reporting unresolved conflicts rose accordingly, which is the honest figure rather than the flattering one.

The static site renders the split rather than flattening it: unresolved conflicts sit under a red alert header, ignored ones under a muted *"N recorded, not blocking"* heading with the rationale shown as **Why it does not matter here**.

## Excerpt page crops (2026-08-14)

**193 of 252 excerpts now commit the page region they were transcribed from.** A recorded SHA-256 detects local drift but proves nothing to a reader who does not hold the document, and almost none of these manuals is publicly hosted — the Stern 24 case makes the point, since its retained PDF no longer matches the digest its source record pins, so nothing that record cites can be re-checked by anyone. The crop travels with the claim.

**Resolution is derived, never chosen.** `tools/render_excerpt_image.py` reads a scanned page's embedded raster against its placed width in points and renders at exactly that native resolution: 150, 200, 382, 400, 414 dpi across this corpus, essentially never a round number and never the 300 dpi a fixed setting would have used. Rendering above native invents pixels; rendering below it discards the connector-table fine print that is usually the reason the crop exists. A born-digital page has no native resolution, so there the tool picks a dpi from the smallest type inside the crop and targets a readable glyph height. The printed `image_derivation` records the page, the crop box, which case applied and any width cap, which is what makes the whole set re-derivable: `tools/rerender_excerpt_images.py` regenerates every crop from its own recorded provenance without re-exercising the judgement that chose the box.

**The size budget is two-tier, and the second tier is a named list.** `tests/test_excerpts.py` held a 100 kB ceiling with the rationale "a crop is a reading aid, not an archive", and this work initially broke it wholesale before anyone noticed the test existed. Tables keep that ceiling, because there the right answer is a tighter crop. A page-scale drawing — a location diagram, schematic sheet or wiring drawing — carries its evidence in callouts spread across the page, so cropping tighter drops the cited thing and native resolution simply does not fit; those get a 1.5 MB ceiling and are enumerated in `PAGE_SCALE_DRAWINGS` rather than detected, so granting one is a visible edit. A second test fails if a named exception no longer exists or no longer needs the allowance, which stops the list decaying into a rubber stamp. 49 table crops were refitted under the ordinary budget by `tools/fit_excerpt_images.py`, which narrows the pixel budget per file and rewrites the derivation string wherever a curator records it. Committed crops total 42.8 MB.

Two things worth carrying. **An excerpt takes one image while many locators span several pages**, so where a transcription covers a parts list continued across two pages, or four unrelated board drawings, the crop shows the single load-bearing page and the rest is disclosed rather than implied; several excerpts were deliberately left without an image because no single page could honestly stand for the claim. And **a per-machine test must defer to the shared budget rather than restate it** — `tests/test_congo.py` carried its own 100 kB literal and failed on a legitimate drawing the moment the shared rule gained a second tier.

One pre-existing defect surfaced and was fixed at source: regenerating `curate_eight_ball_deluxe.py` silently dropped `machine.ipdb_id`, because the OPDB import added both identity fields to the committed record but only `opdb_id` to the curator's own literal. `--check` stayed green throughout, since the file matched the curator's incomplete output; only `reports/opdb-identity.json` noticed.
