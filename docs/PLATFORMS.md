# Platforms and addresses

On-demand companion to `docs/INSTRUCTIONS.md`. Read it before step 4 of the per-game workflow: before deciding polarity, `normally_closed`, address availability or flipper-column handling, before binding a printed number to a public address, and before editing `controllers/pinmame/`; it is not loaded by default.
The runbook wins where the two disagree.

**Belongs here:** per-platform read paths and emulator normalization, flipper columns and synthesized inputs, special-solenoid identities, public-address arithmetic, driver game-data fields, and how controller-profile notes are written.

**Does not belong here:** facts that hold on every platform (`docs/INSTRUCTIONS.md`), or one game's addresses (its definition and knowledge note).

## Rules

- On System 3 through System 11 and Data East derivatives, keep a factory manual's printed special-solenoid identity, a community chart's coil number, the PIA handler index, `sxx.ssSw` slot, and PinMAME public output address distinct. Derive the public address from the selected `setSSSol` permutation when the PIA drives the circuit, and from the direct `CORE_FIRSTSSSOL + ii` path when `sxx.ssSw[ii]` supplies switch-driven state; Data East's PIA permutation is not sequential. Preserve only identities actually printed by the cited source—never manufacture SP1-SP6 aliases from sequential public numbers. If game-specific secondary evidence maps physical device names directly to public coil numbers and conflicts with the shared-source derivation, it may be retained as a clearly attributed conflicted working mapping, but every affected binding must stay conflicted and require a LibPinMAME trace before resolution.
- `physical.normally_closed` is a construction fact about the contact the switch matrix sees, never an inference from how an opto beam rests. Where no manual or schematic prints the matrix contact's rest state, derive it from the platform's read path and a runtime proof: on Whitestar, `se.c`'s `switch_r` returns `~core_getSwCol`, so public 1 is the CPU's closed-contact reading, and an opto the known-working script or the ROM treats as active at 1 therefore has a matrix contact that rests open, whatever the beam does. "Not actuated" means the ROM reads the switch inactive: where a mechanism happens to park, or whether a captive ball sits in a beam, does not change the contact's normal state. On the WPC switch-matrix row read the CPU sees `swMatrix` directly (through `core_getSwCol`, or `wpc_pic_r` on security-PIC generations), so a matrix switch outside the inversion mask that the ROM treats as active at public 1 is normally open, and a masked one the ROM treats as active at public 1 is normally closed. The Fliptronic column is read complemented (`WPC_FLIPPERS`/`WPC_FLIPPERSW95` return `~swMatrix`), and a driver can install its own row-read handler for a custom column, so derive those from their own read path. A zero Fliptronic element in a driver's `invSw` therefore does not mean the column is unnormalized; read the generation's flipper-column register handler before calling any 111-118 address unnormalized. A printed "opto, typically closed" halftone marks opto construction; it does not override that derivation for a switch the ROM reads unmasked.
- An address PinMAME never synthesizes is not thereby unreachable. `core_updateSw` rewrites only the flipper-column bits in `locals.flipMask` and preserves every other bit, so a host write to a flipper-column address outside the mask still reaches the ROM through the driver's own read handler. Before recording such an input as unused or unreadable, check whether the driver's read path consumes the bit and prove what the ROM does with it in a harness run; a fitted cabinet input and an emulator that does not synthesize it are two compatible facts, not a conflict.
- On a driver whose flippers are cabinet-wired (`FLIP_SWNO(l,r)` without `FLIP_SOL`), PinMAME's `core_updateSw` rewrites matrix switches `l` and `r` on every update from its own flipper switch column (`CORE_FLIPPERSWCOL`, or internal column 15 on the generations `core_updateSw` names in its `flipSwCol` test) and fabricates the synthetic flipper outputs from the same bits. The address a consumer drives is that column's button bit under the platform's switch conversion, never the printed matrix address, and a write to the matrix address is silently overwritten. Enumerate the whole column, mark as used only the positions the ROM can actually reach, derived from the driver's own read path: a static proof that no read handler can select the column is enough to record the other positions unused, while a read path that can consume the bit needs the previous rule's harness run. Say in each copied matrix switch's notes that it cannot be driven directly. The column's public numbering follows the platform's switch conversion, so derive it from the controller profile rather than carrying it across platforms. A known-working script that writes the matrix address itself has a defect with no effect, and that defect belongs in the device note, not in `conflicts`.
- Controller-group `notes` are literal plain text by default. Set `notes_format` to `markdown` only after rewriting dense technical prose as reviewed GitHub Flavored Markdown with real paragraphs, lists, tables, headings, emphasis, and inline code; nested headings start at level 4 because the platform group is already level 3. Never opt an existing plain string into Markdown mechanically because formulas such as `col*10` can be reinterpreted. Keep short notes plain, preserve every source-backed claim during editorial rewrites, do not embed raw HTML or unsafe link/image URL schemes, and verify the rendered platform page as well as the JSON source.

### Platform read paths and synthesized inputs

- **Fliptronic EOS is synthesized; buttons round-trip.** For each flipper a WPC driver declares with `FLIP_SOL`, `core_updateSw` rewrites the EOS bit (111/113, or 115/117) from the coil's `core_getSol` state after `CORE_FLIPSTROKETIME`; do not drive it, and do not infer physical EOS rest state from it. With keyboard handling off, buttons 112/114/116/118 round-trip; with it on, lower keys are copied into upper button bits lacking `FLIP_BUT`, so keyboard runs prove nothing about fitted upper buttons. (archive L116, L120, L606; verified: `core.c core_updateSw`)
- **System 11 reads the matrix uninverted.** `s11.c` hands the CPU `core_getSwCol` and `s11games.c` leaves `invSw` zero, so a switch the ROM treats as active at public 1 rests open. (archive L584; verified: `s11.c pia4a_r`, `s11games.c INITGAME`)
- **Capcom complements in `io_r`.** Outside the per-game `capInvSw` mask, public 1 is a closed contact; on Kingpin the mask is exactly the opto set. The Switch Test icon shows that level, not the expected rest. (archive L405, L409; verified: `capcom.c io_r`)
- **Cabinet-port rewrites happen only with keyboard handling on.** `core_updateSw` passes the input ports to a driver's switch update only while PinMAME keyboard handling is enabled (`updSw(g_fHandleKeyboard ? inports : NULL)`), and both `SWITCH_UPDATE(by35)` and `SWITCH_UPDATE(by6803)` rewrite cabinet switches only `if (inports)`. A direct-switch scenario therefore reaches every one of these addresses; a scenario with named key actions does not. The ports differ by driver. `by6803` writes 6 (Credit), 9-11 (coins), 14 (Slam Tilt) and 15 (Ball Tilt) on every generation, and on `GEN_BY6803`, which has the coin-door keypad, also the keypad's sixteen keys on the low four rows of columns 1-4: public 1-4, 9-12, 17-20 and 25-28, with the coin switches 9-11 sharing keys 3, 2 and 1. It leaves 5, 7, 8, 13 and 16 alone, so the BY35 port layout does not transfer to Beat the Clock or Special Force. The keypad positions are matrix positions that playfield switches share: Special Force's manual says its playfield switches are wired in parallel with the keypad, and its Switch Test names public 2, keypad 0, CHOPPER TOP. (2026-10-01 harness pass review; commit "defs: settle Special Force's legacy conflicts from its service tests"; verified: `core.c` `core_updateSw`, `by35.c` and `by6803.c` `SWITCH_UPDATE`, `by6803.h` `BY6803_COMPORTS`, `by6803games.c` `INITGAME6803`, the VPinMAME `6803.vbs` keypad constants)
- **No WPC generation has a game-on output at 19.** The legacy platform map's `ROM Started` (alias `c_game_on`) at solenoid 19 is wrong on WPC; the game's own T.5 flasher test or mechanism test names what 19 is. On BY35, 19 is the flipper-enable relay, held from Start to game over; on System 11, the game-on line is 23. (commits settling Black Rose, No Fear, NBA Fastbreak, Doctor Who, Road Show, Skateball and Diner)
- **PinMAME does not model Data East alpha switch-driven special solenoids.** `INITGAMES11` leaves `sxx.ssSw` empty, so `setSSSol` publishes 17-22 only when the ROM drives a PIA special line itself; on 2026-10-01 a run that closed every bumper and sling switch on five ROMs published none of them. Map them from wiring evidence or ROM analysis, not a gameplay run. (commit "defs: record the tried Data East special-solenoid run in five conflicts"; verified: `degames.c INITGAMES11`, `s11.c setSSSol`)

- **Stern MPU-200 lamps are discrete SCRs on four decoders, and the flippers publish four outputs.** A public lamp is `16 * k + a + 1` for decoder `U(k+1)` output `S(a)` (the BY35 lamp strobe), each decoder line carries a resistor `R<n>` that ends at SCR `Q<n>`, and the pin-to-SCR table is on the same Lamp Driver Schematic, so read all three from the game's own sheet. Two output pairs are easy to transpose when a sister game's table is reused (S7/S8 of the second decoder drive Q25/Q24, S9 of the third and fourth drive Q41/Q46). A flipper button press asserts a synthetic pair, 45/46 and 47/48, together and for the whole closure with no pulse shaping (`core.c` sets both bits of each pair); the Stern MPU-200 profile declares only 46 and 48. (knowledge note `knowledge/stern/quicksilver-1980.md`; verified: `core.h` `sLRFlip`/`sLLFlip`, `by35.c` `by35_lampStrobe`)
- **A masked Fliptronic position reads the public level directly, and the ROM may fire a flipper from either opto of its button.** WPC-95 complements the flipper column on read, so a position the driver's mask also inverts (NBA Fastbreak's Cust bit 0x10, public 115) reaches the ROM uncomplemented: public 1 is a raw open contact, and a switch the ROM names at 1 there rests closed. A game with lower flippers only can still wire each cabinet button's second opto to F6/F8; NBA Fastbreak's ROM fires the lower flipper from 116 and 118 as from 112 and 114. Its own wiring pages rebut the parts list's NOT USED, so record such a position as the same button's second opto with the button's role. (knowledge note `knowledge/bally/nba-fastbreak-1997.md`)

### Addresses, numbering and driver fields

- **Printed numbers are aliases.** A Self Test # column, a schematic's "column 9", a custom board's item numbers and printed flipper circuits are `manual.address` or `manual.self-test` aliases, never bindings. Run the ROM's own test where it displays each number as it fires. (archive L648, L668, L672, L690)
- **Derive public addresses from pinned core arithmetic.** Compute `CORE_CUSTSWNO` (on WPC the first custom column is public 121) and `CORE_CUSTSOLNO` (first is 51) in code, and triangulate with the script and a structural proof; a manual agreeing with a stale driver comment does not overrule that. Verify each table on a page separately: two can follow different rules. (archive L689, L703, L780, L847, L858; verified: core.h:302,330,335-347)
- **Compute masks and macros in code.** Map `invSw` through the driver's own `sw2m`, never by array position. Decode each file's own `INITGAME*` macro against `core_tGameData.hw` (`flippers, swCol, lampCol, custSol, soundBoard, display, gameSpecific1, ...`); BY35's fifth argument is `lampCol`, and System 11's `db` is `display`. (archive L762, L849, L894, L910; verified: core.c `core_setSw`, by35games.c:32-33, s11games.c:38-40, s11.h:220-226)
- **Re-read each game's own fields.** BY35 continuous outputs 17-20 and any extra strobe, System 11 `muxSol`, `gameSpecific1` and GI relays, Data East display arrays and `FLIP_SWNO` numbers differ per game; never copy a sibling's. Check whether the game has a GI channel at all. (archive L781, L803, L895, L911, L917, L996, L997; verified: by35.c:240-241, lisy35.c `lisy35_set_variant`)
- **Take the platform from the game's `GEN_*` value.** Use the root driver's game-data generation, not its machine-module symbol, an analogy or the brief: a module is shared across generations. (archive L163, L173, L185, L205, L685; verified: gen.h, stgames.c:229, tools/attach_pinmame_io.py)
- **A lamp chart's transistor pairing is per game.** The LDA-100 board's decoder order is shared by Stern MPU-200 machines, but a ROM sweep is what proves it: on Star Gazer public lamps 24 and 25 reach Q25 and Q24, crossed against the order Ali's curator carries, and the chart prints Q27 on the row for connector pin J1-5 where the lamp-driver schematic draws Q24. Pair each public lamp with its chart row through a ROM behaviour (a sweep order, a named lamp the script reads, a sign lamp a switch lights) before copying a sibling's table; solenoids likewise, since the printed test numbers are driver positions and the public order differs. (knowledge/stern/star-gazer-1980.md)
- **Pinball 2000 lamps are bit index plus one, and its optos are active-high.** P2K sets no `MDRV_LAMP_CONV`, so it inherits the default `core_swSeq2m`/`core_m2swSeq`: `vp_getLampIndex(n)` reads bit `n - 1`, changed-lamp reports return bit index plus one, and manual cell `<column><row><bank>` is public `(column - 1) * 16 + (bank B ? 8 : 0) + (row - 1) + 1` (`11A` = 1, `88B` = 128). That held at every revision; a zero-based `p2k_names.h` hid it until upstream cc2296d8 renumbered the table, so never take a public number from a debug name table without the core conversion. From b7a60eb0 (upstream ccba7199) `MACHINE_INIT(p2k)` declares the per-game opto list in `coreGlobals.invSw`, so every public P2K switch is active-high (`1` = beam blocked) while the board still reads the optos raw active-low; traces recorded on older revisions carry the raw low level. The same pin (upstream 4ea35501) maps key 8 to Down (102) and key 9 to Up (103). (knowledge/bally/revenge-from-mars-1999.md; verified: `core.c` `core_swSeq2m`, `vpintf.c` `vp_getLampIndex`, `p2k.c` `MACHINE_INIT(p2k)`/`SWITCH_UPDATE(p2k)` at b7a60eb0)
- **A task brief is not evidence.** Count mechanism instances in the script and the sources; when the brief is wrong, record the correction rather than the brief's framing. (archive L726, L795, L838, L904, L921)
- **A Data East DMD ROM drives the six switched solenoids itself, and its own coil test pairs printed number and public address.** The alpha games' special solenoids are not publishable from a run (the lesson above), but a DMD ROM writes its PIA special lines, so 17-22 appear. `tftc_303`'s Cycling Coils test fires public 17-22 in order under the names `LEFT TURBO`, `BOTTOM TURBO`, `RIGHT TURBO`, `LEFT SLING`, `RIGHT SLING` and `LASER KICK 50V`, so the manual's printed coil numbers are the public addresses there; re-prove it per game rather than carrying it over. (commit "defs: curate Tales from the Crypt from its manual, service tests and retained table"; verified: `s11.c setSSSol`, `ssSolNo`)
- **A Data East custom solenoid is public 51 and up, whatever the driver comment says.** Tommy's `tommyGameData` declares `custSol = 1` with a `getSol` handler returning `core_getSol(44) > 0` for `CORE_CUSTSOLNO(1)`, commented `/* 33 */`; `CORE_FIRSTCUSTSOL` is 51, so the blinder is published at 51 as a copy of CN3 line 44, and its retained ROM moved only 44 and 51 of 37-51. Record such an address as the physical device and the printer line as its source, with a `direct` relationship between them. (commit "defs: curate The Who's Tommy Pinball Wizard from its manual, service tests and retained table"; verified: `degames.c` tommyGameData, `core.h` CORE_CUSTSOLNO, `core.c` core_getSol)
- **`S11_PRINTERLINE` publishes PIA2 port B at 37-44.** A Data East DMD game that sets it gets eight virtual outputs there (`s11.c pia2b_w`, `extSol`, read by `core_getSol` for `GEN_ALLS11`); Guns N' Roses uses them for its magnets, and Tales from the Crypt's ROM writes them only for its audit printout (Adjustment 61: public 40, 42, 43 and 44 together). Such addresses are `used` virtual outputs, not unknown ones, once a run shows what drives them. (commit "defs: curate Tales from the Crypt from its manual, service tests and retained table"; verified: `degames.c INITGAMES11`, `s11.c pia2b_w`)
- **A service test sweeps unfitted drivers, and a ROM may name cabinet-copy switches differently from the manual.** Tales from the Crypt's Cycling Coils pulses public 12, 13 and 14 and names them `NOT USED`, which agrees with the wiring diagram's NO COIL AT THIS LOCATION; the pulse is the sweep, not fitment. The same ROM calls matrix switches 63 and 64 `LEFT FLIPPER` and `RIGHT FLIPPER` where the manual's chart prints End of Stroke, and `core_updateSw` fills them from the flipper column, so a consumer still drives 84 and 82. (commit "defs: curate Tales from the Crypt from its manual, service tests and retained table")
