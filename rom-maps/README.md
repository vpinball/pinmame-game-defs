# ROM maps

Each file maps the firmware of one memory layout of one physical machine: game and mode state, operator adjustments, audits, replay levels, sound commands, and recipes that start each mode from a table script. This is supplemental knowledge. It never feeds a machine definition, and it does not count toward `coverage`, `completion_score` or `author_ready`.

Path: `rom-maps/<manufacturer>/<machine-slug>-<year>.<map-id>.json`, where `map-id` is the PinMAME set whose memory layout the file describes. `roms` lists every driver of the machine that shares it. For each entry, `verified_on` records actual verification scope; `applies_to` records applicability or source-declared compatibility and does not establish verification. An upstream map's compatible-ROM list alone supports candidate evidence with an empty `verified_on` list.

## Format

A ROM map wraps a complete [Pinball Memory Maps](https://github.com/tomlogic/pinball-memory-maps) document under `memory_map`. That part validates against the upstream schema vendored in `_vendor/map.schema.json`, allowing direct structural comparison. Its `_metadata.version` is the local derivative map's version, independent of the upstream source revision; contribution back upstream requires reconciling metadata and evidence with that project. CPU addresses inherited from upstream may be integers or hex strings; new descriptors use hex strings. `extensions.addressing` records whether they also equal the raw `Controller.NVRAM` index.

What that format has no section for goes under `extensions`:

- `mode_state`: named game- and mode-state bytes, as upstream descriptors.
- `replay_levels`: the replay thresholds.
- `sound_commands`: the protocol, plus every command with its class and, where known, a label, a sample name and a note. Sample names are carried only where their source's terms allow it.
- `mode_replay`: the ROM's switch timing, the running-mode word, and one recipe per mode with its precondition and its verification. The shape is adopted from the Attack From Mars mode-replay data.

`evidence` is keyed by JSON Pointer. An entry covers that descriptor and everything beneath it, and `python -B -m pinmame_game_defs validate` fails when any descriptor, command or recipe is left uncovered. Status uses the definitions' vocabulary: `candidate`, `observed`, `validated`, `conflicted` or `deprecated`. The schema requires observed and validated entries to name at least one verified ROM; for `validated`, it also requires the self-declared proof list to include `manual` or `harness`. These are structural checks: the validator does not verify the underlying manual or harness artifacts or establish that a harness used pinned PinMAME. Curators must substantiate those claims from retained evidence before assigning the grade.

The files are generated by `tools/curate_rom_maps.py` from the vendored maps and the pinned tables in `tools/rom-map-inputs/`. Run it with `--check` to refuse drift.
